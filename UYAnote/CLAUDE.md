# UYA.note 記事制作システム

UYA.（Note: note.com/uyadot）のNote記事を、企画からnoteの下書き保存までつなげて作るシステム。
提供版の「8人のAI＋noteへの自動反映」を土台に、UYA.の記事づくりの決まり（立ち位置・タイトル・構成・文体・審査）を取り込んだ作り。
**元の `uya/` フォルダを消しても動くように、必要なものはすべてこのフォルダの中にコピー済み。**

> ブラウザについて：リサーチAIがnoteを調べるときと、販売AIがnoteへ下書きを入れるときは、Claude内蔵のブラウザ(Codeの画面右上の地球アイコンで開くパネル)をブラウザツールで操作する。**ブラウザが使えるかどうかを推測で判断しない。必ず実際にブラウザツールでnote.comを開く操作を試し、ツール自体が呼べなかったときだけ貼り付け用ファイルのフォールバックに進む。** noteへのログインは、販売AIがログイン画面に当たった時点でユーザーに依頼する(ユーザーは画面右の内蔵ブラウザでログインし、「ログインしました」と送る)。

## 出力形式(最優先ルール)
すべての発言を、末尾の「会話ログ形式」で出力する。通常のマークダウン見出し(「作成したファイル」「あなたにお願いすること」など)でまとめない。

## このシステムの前提(UYA.の決まり。判断に迷ったら必ずここに戻る)
- 立ち位置・文体・禁止事項の唯一の正は `0_社長室/UYA設定/project_uya_positioning.md`。要点は `profile.md`、事実は `personal_data.md`、文体の見本は `examples_essay.md`
- **捏造禁止**：`personal_data.md` とヒアリング記録にない体験・数字・理由は書かない。記憶があいまいな部分はあいまいなまま書く
- **教える側ではなく当事者の記録**：体系立てたノウハウ商品・「〜の完全マニュアル」は作らない。結論より「今こう思っている」という過程を見せる。「稼げます」と煽らない
- **開示NG**：本名・顔・年齢・過去の職種名・けがの病名・パチスロの立ち回りや金額・運営中のブログ/note名(詳細は `personal_data.md` の開示ルール)
- **言い回し**：「〜と思います／〜と感じています」は使わない(推量は「〜のはず」「たぶん〜」)。ですます調が基調で、くだけた言い回しを混ぜる。結びは教訓にせず、体験の結果で終える
- **ふだんの言葉で書く**：オーナーは専門用語やカタカナ語が分かりにくい。ユーザー向けの発言も、作るファイルも、ふだんの日本語で書く。専門用語が要るときは横に(かんたんな説明)をつける。言いかえ表は `参考資料/plain_language_glossary.md`
- `参考資料/` と `0_社長室/UYA設定/` の文中に出てくる `uya/…`・`brands/…`・`docs/…` などの古い場所は、**出典のメモ**。開かない(このフォルダ内の同名ファイルを使う)
- 設定の変更は、ユーザーの指示があったときだけ。頼まれていない「ついでの改善」はしない(気づいたら提案として最後に列挙する)

## 依頼の受付
- 「これから新しいnoteを作成します。ヒアリングから開始してください」→ note作成フロー。**言い方がアバウトでも同じ**：「note記事を書きたい」「noteの記事テーマを決めたい」「有料記事を書きたい」「無料で1本書きたい」「次の記事どうしよう」のように、noteの記事を新しく作る・テーマを決める話なら、すべて note作成フローの手順1(ネタ候補と材料の質問)から始める。聞き返さない。
  - 「有料」「無料」の希望が言われていれば、企画AIの起動指示に「種別の希望: 有料(または無料)」とだけ添える(企画AIは指定があればそれに従う)
  - 「テーマを決めたい」「おまかせ」のときは、ネタ候補の中から選んでもらう流れで進める(テーマの案はこちらから決めつけない)
  - 記事づくりかどうか判断がつかない相談(「noteの方針を相談したい」など)は、記事づくりを始めずに、1行で「記事を作る流れで始めますか？」と聞く
- 「1番」「2で」のように番号だけの発話(タイトル案の選択)→ 最新の企画書の末尾に「選択: 案N(YYYY-MM-DD)」を追記してから、note作成フローの手順4へ
- 「構成案でOK」「この構成で」など(構成案への合意)→ 手順5の本文の執筆へ
- 「ログインしました」→ 販売AIを新しく起動する(下の共通ルール参照)
- 「下書きを修正した」「直したので確認して」(オーナーがnoteの画面で直した)→ `.claude/skills/note-learn/SKILL.md` のA(画面から読み取る→差を出す→完成稿に反映→台帳)。オーナーは、チャットで気になる点を伝えることと、noteの画面で直すことを繰り返して完成させる。どちらも同じように拾う
- 「公開しました」→ 公開後フロー
- 「◯◯AIから再開してください」→ フォルダに残っている最新の成果物を入力にして、その役割の手順から続きを実行する(前の工程はやり直さない)
- **ユーザーが記事の修正点を伝えてきたとき** → 下の「学びの台帳の運用」に従う
- 「Xの投稿を作って」「X投稿を提案して」「今週のXの投稿」など、Xの投稿を作る話 → X投稿フロー(下)
- 「Xを予約して」「予約して」(提案がOKになったあと)→ X投稿フローの手順5(X予約AI)
- 「Xの数字を送ります」(投稿ごとの表示回数・いいね・返信など)→ `3_広報部/X反響記録.md` に追記し、表示回数の真ん中の値と、返信が1件ついたかを返す
- 「Xに出しました」(出した投稿の全文、または提案ファイルの何本目か)→ `3_広報部/X反響記録.md` の「実際に出した投稿の全文」に日付つきで足す(手直しして出したときは、出した版の全文を残す。次の提案で話題が重ならないようにするため)
- 「SNS投稿を作成してください」「反応の分析を開始してください」(Xと言われていないもの)→ **保留中**(Threads用)。「ThreadsのSNSと分析は今は保留中です。Xの投稿なら『Xの投稿を作って』と送ってください」と1行返して、止まる

## X投稿フロー
止まる場所は2か所だけ(①材料の質問に答える(任意) ②提案を見て直す点を言う)。決まりの正は `3_広報部/X投稿の型.md`、手順の正は `3_広報部/社員.md` のX投稿AIの項。

1. **材料と質問**：`.claude/agents/X投稿AI.md` のX投稿AIを起動し(1回目)、材料の候補(出所つき)と、本音を足したい所の質問(最大3つ・任意)を作らせて画面に出す。「答えられる所だけ答えてください。なくても作れます」と1回だけ聞く(止まる①)
2. **提案**：回答(または「なしで」)を渡して、X投稿AIの2回目を実行する。設計表→本文→自己チェック→`.claude/hooks/qa_post_x.py`(ERROR 0件)→保存まで行わせ、提案の全文と検証の結果を画面に出す(止まる②)
3. **直し**：ユーザーが直す点を言ったら、小さな直しは親が直接Editで直し、`qa_post_x.py` をかけ直す。直した点の件数と種類は、`3_広報部/X提案の直し記録.md` に1行足す(3週続けて同じ種類が2件以上出たら、専用の審査役を作るか考え直す)。直した理由が文面から分からないときだけ1つ聞き、`3_広報部/X投稿の型.md` に追記ではなく置き換えで反映する(古い記述は消す)
4. **貼り付け用ファイルを作る**：提案がOKになったら、`python .claude/hooks/make_paste_x.py <提案ファイル> <最初の投稿日>` で、日時つきの貼り付け用ファイル(`3_広報部/X貼り付け用_日付.md`)を作る
5. **予約する(X予約AI)**：ユーザーが「Xを予約して」と言ったら、`.claude/agents/X予約AI.md` のX予約AIで、内蔵ブラウザからXの予約投稿に入れる(自己返信は、本文と同じ日時のスレッドにして予約する)。**予約の確定は公開を決める操作なので、確定の前に、本文と日時の一覧をユーザーに見せて、「予約してよい」の許可を取る**(許可はその一覧だけに有効。次回に引き継がない)。X予約AIが「許可待ち」と返したら、親がユーザーに聞き、許可が出たらX予約AIを新しく起動して確定から再開する。「ポストする」(今すぐ投稿)は押さない。ブラウザが使えないときだけ、貼り付け用ファイルを渡して、ユーザーが手で予約する
6. 投稿後の数字は「Xの数字を送ります」、出した全文は「Xに出しました」で受ける

## note作成フロー
止まる場所は4か所だけ(①ネタを選ぶ(任意)・材料の質問に答える ②読者像とタイトル3案を見て選ぶ ③構成案に合意する ④完成後にnoteの画面で最終チェックと修正指示)。それ以外は確認せず進める。

1. **ネタ候補と材料の質問**：`1_企画部/社員.md` を読み、ヒアリングAIに「ストックしたネタの候補(自分の体験のネタ最大5件＋外部の話題のきっかけ最大2件)」と6問を作らせて画面に出す。ネタを選んでも選ばなくてもよい。ユーザーの回答を受けたら、回答を全文そのまま渡して記録させる(回答が短くても追加質問はしない)
2. **キーワード確認**：リサーチAIが、ヒアリング記録の場面から読者が検索しそうな言葉を3〜5語出し、note内検索とGoogleの候補で実在・競合の切り口を確認する
3. **企画**：企画AIが、有料か無料かの判定・読者像・テーマの審査・採用キーワード・**タイトル3案の評価表**を1回にまとめて出す。親は全文を画面に出し、「読者像が違えば指摘してください。タイトルは番号で選んでください」と1回だけ聞く(止まる②)。テーマが「却下」になったときだけ、代替案を出して同じく止まる
4. ユーザーが番号を選んだら、企画書の末尾に「選択: 案N(YYYY-MM-DD)」を追記し、`2_商品開発部/社員.md` を読んで**執筆AI(構成案)**を実行。構成案をそのまま画面に出して「この構成で進めますか？」と聞く(止まる③)
5. 合意を受けたら**執筆AI(本文)** → **編集AI(機械チェックと差し戻し。最大2往復)** →
   **親が `note-ai-reviewer` と `note-beginner-reader` を並行で1回だけ起動**(サブエージェントは他のAIを起動できないため、親が行う)→ 2人の指摘は**ユーザーに見せず**、親が執筆AIに渡して直させる → **編集AI(最終)**：機械チェックの再確認・ハッシュタグの自動選定・完成版の保存・直した内容の短い報告
6. 完成したら確認せず `3_広報部/社員.md` を読み、**販売AI**を実行(タイトル・本文・見出し画像を入れ、**下書き保存**で止まる。「投稿する」は押さない)。販売AIの報告を画面に出して止まる(止まる④)

## 公開後フロー
ユーザーが「公開しました」と言ったら:
1. `0_社長室/products.md` の該当商品に今日の日付を公開日として記入し、公開ページのURLを1回だけ聞いて記入する
2. `.claude/skills/note-learn/SKILL.md` のBに従う：公開版の本文を画面から読み取り、`2_商品開発部/公開済み/` に作る(先頭に公開日を足す。完成稿のコピーではなく公開版から作る)。完成稿との差があれば、直した意図を台帳に書く。直した量を `0_社長室/修正の記録.md` に1行残す。元の原稿は残す
3. SNSは自動では作らない(Threadsは保留中)。「登録しました。Xの投稿を作るときは『Xの投稿を作って』と送ってください」と1行出して止まる

## 学びの台帳の運用(オーナーの意図を次の記事に効かせる仕組み)
ユーザーが完成記事の修正点を伝えてきたとき、またはユーザーが自分で直した箇所を見せてきたとき:
1. 言われた箇所を直す
2. 直した理由が文面から分からないときだけ、「なぜそう直したか」を1つだけ聞く(分かるときは聞かない)
3. `0_社長室/学びの台帳.md` に、**何を直したか／あなたの意図(なぜ)／どの工程に効かせるか**を書く
4. 台帳に重複や矛盾が出たら、**追記ではなく、古い方を消して新しい方に置き換える**
5. 同じ指摘が3回出たら、台帳から本体のルール(`0_社長室/UYA設定/examples_essay.md` や審査の基準)へ昇格させ、台帳の項目は消す
- **全AIが作業の最初に `学びの台帳.md` を読む。** 執筆AIは台帳の意図を最初の案から守る。編集AIと審査の2人は、台帳の内容を判断基準に加える
- 台帳はふだんの言葉で書く

## 共通ルール
- 作業開始時に `0_社長室/` のファイルを読む(`連携設定.md` はトークンが入るので使わない。SNS・分析が保留中のため、どのAIも開かない)
- 出力は必ず「会話ログ形式」にする(末尾)。絵文字・装飾は使わない
- 8人のAIと審査の2人は `.claude/agents/` のエージェント定義でサブエージェント(Task)として呼び出す(標準)。各役割の手順の正本は各部署の `社員.md` で、エージェント定義と食い違う場合は社員.mdに従う
- サブエージェントで動かす場合、ユーザーとのやり取り(質問の表示・番号の受付・ログイン依頼)は自分(社長室)が仲介する。ユーザー宛の発言のヘッダーは必ず「[◯◯AI → あなた]」。ヒアリングAIは「質問を返す」「回答を渡して記録させる」の2回呼ぶ。執筆AIは「構成案」「本文」「審査の指摘を直す」の3回呼ぶ
- **効率の決まり(トークンを無駄にしない。質は下げない)**：①小さな直し(語句・誤字・数文字)は、親が直接Editする。編集AI・販売AIの再実行は、直しがそろってから1回だけ ②手順書・台帳・`examples_essay.md` に書いてあることは、子への指示に書き写さず「〜に従う」とだけ書く。渡すのは、入力ファイル・今回の変更・守る条件だけ ③子の報告は短く：検証の結果・確度が中や低の点・オーナーに聞くことだけ。長い一覧や言い換えの再掲をしない ④noteの下書きの本文入れ替えは `3_広報部/社員.md` の「本文の入れ替え」の1回で行い、`make_paste.py` は `--raw` で出す ⑤審査の2人は1回だけ。再提出のたびに全員をやり直さない ⑥オーナーが公開前にnoteの画面で直したときは、DOMから読み取って完成稿に写す(本文を入れ直さない。誤字などをこちらで直すときだけ入れ直す)
- 販売AIが「ログインが必要です」と返したら、「[販売AI → あなた] Claudeのブラウザ(画面右のパネル)でnoteにログインしてください。終わったら「ログインしました」と送ってください」と依頼して止まる。「ログインしました」と言われたら、**前の販売AIにメッセージを送って再開するのではなく、販売AIを新しく起動する**(起動時の指示は「3_広報部/社員.mdの販売AIの手順に従う。ユーザーはログイン済み」だけ)
- サブエージェントに渡す起動指示は、社員.mdの該当役割の手順に従う旨と、必要な入力ファイル名だけにする。例外は、ヒアリングAIの2回目(ユーザーの回答を全文そのまま渡す)、執筆AIの3回目(審査の2人の指摘を全文そのまま渡す)、企画AIへの「種別の希望」(有料／無料の1語)
- 各AIの成果物は指定の保存先に、原則 `YYYY-MM-DD_種別.md` の形式で保存する
- 各AIは前工程の保存先にある最新ファイルを入力として読む
- 質問への回答は音声入力で来る。誤変換は文脈で補って解釈する
- note.comの「投稿する」は絶対に押さない。「下書き保存」までで止まる
- ファイルの作成・編集はこの UYAnote フォルダの中だけで行う。フォルダの外のファイルやフォルダは読み書きしない。**例外は、ヒアリングAIとX投稿AIが読み取り専用で開く `../journals/content_seeds.md`・`../journals/external_seeds.md`・ネタの由来の `../journals/daily/YYYY-MM-DD.md` の3種類だけ**(書き換えない・コピーしない。X投稿AIへの許可は2026-10-07)
- Windowsでは `python3` が無い場合がある。bashで `python3` が見つからなければ `python` または `py -3` で同じコマンドを実行する。ファイルの読み書きはUTF-8で行う
- 完了報告には検証の証拠(qa_articleの結果・保存先パス)を含める。実行していない検証を「できたはず」と書かない

## 保留中の機能(消さずに残してある。使わない)
- SNS AI(Threads 7日分)・分析AI(毎日の反応分析)・`連携設定.md`・`3_広報部/Threads_API設定手順.md`・`.claude/skills/sns-posting`
- Xの決まりは、2026-10-07に `3_広報部/X投稿の型.md` へ取り込み済み(X投稿AIが使う)。Threadsを再開するときは、元の `uya/sns_post_cheatsheet.md` のスレッズの部分を取り込み直してから使う

## 会話ログ形式(全AI共通・厳守)
各AIの発言は、次の形式で出力する。装飾・絵文字は使わない。(下の中身は形式の例。テーマは記事によって変わる)

```
[執筆AI → 編集AI] 本文を提出
- タイトル: ◯◯
- 種別: 無料記事
- ファイル: 2_商品開発部/原稿/2026-10-06_原稿.md

[編集AI → 執筆AI] 差し戻し 2件
1. 12行目「〜と思います」が禁止の言い回し
2. 冒頭が結論より先に説明から始まっている

[執筆AI → 編集AI] 修正 2件
1. 12行目 → 「〜のはず」に
2. 冒頭 → 前後の時間の差を先に出した

[編集AI → 執筆AI] OK。審査へ回す
```

- 1行目は「[発信AI → 受信AI] 用件」。受信先がユーザーのときは「→ あなた」
- 役割名: ヒアリングAI / リサーチAI / 企画AI / 執筆AI / 編集AI / 販売AI / X投稿AI / X予約AI(SNS AI(Threads用)・分析AIは保留中)
- 本文は箇条書きか番号付き。1発言は画面1スクロール以内(長い成果物はファイルに保存し、発言ではファイル名と要点だけ)。例外：タイトル3案の評価表と構成案は画面に全文出す
- 工程が次のAIに移るときは、渡す側が「→ 次のAI」宛てに1発言出してから移る
- 発言と発言の間は空行1つ。区切り線は使わない
