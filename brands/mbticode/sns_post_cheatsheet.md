# ▼ 生成ワークフロー（唯一の正・毎回この順序で実行）

**Step 1. 資料を読む（内容の正確性のため必須）**
- **タイプの行動を書く投稿は、書く前に `reference/MBTI各タイプ傾向まとめ.txt`（詳細版）の該当タイプの節を必ず読む。** 簡易版（`mbti_quick_ref.md`）だけで行動を書かない。ラブタイプは `lovetype_sns_ref.txt`（詳細が要るときだけ `ラブタイプ各キャラクター傾向まとめ.txt`）。恋愛系トレンドワードを使うときは `trend_words_bank.md`。
- 「▼ 内容の正確性」のチェックを、生成のあいだ守る。

**Step 2. ネタを選ぶ**
- `neta_ledger.md` の「ネタ在庫」で、状態が「未使用」のものから選ぶ。**直近1週間（`python brands/mbticode/tools/show_queue_recent.py`）と、系統・形・タイプの主張が重ならない**ものにする。同じタイプ・同じ主張の骨子を、直近7日＋今回の分で繰り返さない（言い方を変えただけの焼き直しもNG）。
- 案ごとに「どのパターンに沿うか／新しく試すか」を1行で言えること（`analysis/patterns.md`）。確度が低いパターンは1つずつ変えて試す。
- 在庫が10件を切っていたら、オーナーに伝える（補充は予約実行。待てないときは `/mbticode-neta`）。
- Xは `posts_x.txt` の残存分で重複を確認する（運用再開時のみ）。

**Step 3. 生成して検品する**
- バッチを**一時ファイル** `posts/_batch_MMDD.txt` に書く（形式は「▼ 投稿ファイルの書き方」）。投稿ごとに、**使った資料の記載（`MBTI各タイプ傾向まとめ.txt` のどの記載から導いたか）を1行で言える**ようにする（報告の根拠の表になる）。
- **検品**：`python brands/mbticode/tools/publish_batch.py <一時ファイル>`（確認のみ）で **ERROR 0件**にする。Windowsでは `python` が動かないことがあるので `py -3` を使う。Xは `python brands/tools/qa_post.py <ファイル> --account mbticode --platform x`。
- WARNは削除・自己判断で潰さず、報告に全文転記する。ただし**文章を良くする直しは行ってよい**（締めの依頼文・予防線・「残り」の誤用などは直す）。文字数WARN（100〜350字の外）は、短い投稿が目的の場合は残す。
- **外部の投稿を参考にした項目は、保存・投入の前に類似チェック**を行う：元ネタの核と自分の核を1行ずつ書いて着想の近さを判定（中は書き直す・高は使わない）＋`py -3 brands/tools/check_similarity.py <一時ファイル> --sources <元ネタの本文ファイル>`（`=== ID` 区切りの一時ファイル。**リポジトリには保存しない**。元ネタの本文は `py -3 research/export_sources.py <URL…>` で作る。10字以上はWARN・20字以上はERROR）。
- **確認役（バッチごとに1回）**：`mbticode-post-reviewer` に下書きのパスと、「資料から導けない断定がないか見てほしい」という依頼を渡す。指摘のうち、実在しない機能・事例の一部にしか当てはまらない結び・資料にない断定を優先して直す。指摘に対する修正は2回まで。
- 確定前の壁打ちが必要な場合（新しい型の試験など）は `/post-review` を通す。

**Step 4. オーナーに見せる（保存の前）**
- **投稿の全文をチャットに出す**（保存先だけを伝えて終えない）。あわせて、①資料の根拠の表（投稿ごと） ②検品・類似チェック・確認役の結果 ③注意点（資料から細部までは導けない行動など） ④誘導の有無と日時 を添える。
- オーナーのOKを取ってから、保存する。

**Step 5. 保存・投入**
- **Threads**：`py -3 brands/mbticode/tools/publish_batch.py <一時ファイル> --apply`（検品 → CSV変換 → 投入〈過去時刻・重複は自動スキップ〉→ 読み戻し照合まで一括）。手作業のパース・シートの手編集は禁止。
- **X**：`posts_x.txt` に対象分を末尾追記する。7日より古い分は `posts/archive/` へ移す。
- URL誘導の自己リプライは、`posts/cta_templates.md` の承認済みの平たい文から選び、本文とセットで書く。新しい文は、オーナーのOKのあとに同ファイルへ追記してから使う。
- **すでにシートにある未投稿の行を差し替えるとき**は `py -3 brands/mbticode/tools/replace_queue_rows.py <一時ファイル>`（確認表示）→ 承認後に `--apply`。`update_threads_queue_body.py` は、古い自己リプライとURL返信が残るので、差し替えには使わない。
- 投入が成功したら、一時ファイルを削除する（正はシート）。使ったネタは、`neta_ledger.md` の状態を「使用（日付・投稿の日時）」に更新する。

**Step 6. 完了報告**
- 検品の結果（ERROR/WARN件数）・シートに入った行数と日時・使ったネタID・`check_queue_coverage.py` の残り日数を、1〜3行で報告する。
- `py -3 brands/mbticode/tools/check_queue_coverage.py` でキューの残り日数を確認する（足りないときは次のバッチを提案する）。
- 週次クラウドルーティン産のバッチは `_pending_batch.json` → `apply_pending_batch.py` 経由（手順は同スクリプトのdocstring）。

# ▼ 内容の正確性（`reference/` を踏まえた提案にするための確認）

意味の判断が要る項目。機械では見られない。
- [ ] タイプの行動を書く投稿は、詳細版の該当節を読んで書いた
- [ ] 本文の主張が、資料に書かれた特性から自然に導ける。資料にない行動は断定せず「〜やすい」「〜がち」「傾向」で書く。**資料と逆向きに書かない**（例：ENFPは「最初の情熱が冷めると一貫性の維持が困難」）
- [ ] 「なぜこのタイプにこのパターンが出やすいか」を1行で言える
- [ ] タイプ名は「アルファベット＋（日本語名）」で、日本語名は公式の表記（INFP（仲介者型）／ESFJ（領事官型）／ISFP（冒険家型）／ENFJ（主人公型）／ISFJ（擁護者型）／ENFP（運動家型）／INTP（論理学者型）等）
- [ ] MBTIの軸の名前を取り違えていない（N＝直観、S＝感覚）。他アカウントの投稿をそのまま転用しない
- [ ] 実在人物を想起させる断定、特定の人やタイプを傷つける決めつけ、断定的な統計（「〇割は〜」）を書いていない（`brands/CLAUDE.md` 絶対遵守ルール3）
- [ ] 発信者の確定した実体験に読める書き方をしていない（`rules/style_0930.md` 11）

# ▼ 採用しない型

| 型 | 排除理由 |
|---|---|
| 攻撃的ラベリング型（「異常者」等／「〜なだけだよ」と決めつけて閉じるキャラ付け含む） | 炎上リスク・ブランドと矛盾 |
| 議論誘発型（「〇〇って偏見だよね」系） | リプライは多いが保存率が極低く、転換率ゼロ |
| エンタメ消費型（DSKBの笑い文脈） | 保存されず有料記事への動線にならない |
| タイプ主語の断定的愚痴・お説教型（「F型は〜」「ISFPは〜」等で名指し批判） | 「責められない分析」と矛盾。数値が大きくても採用しない |
| 断罪型（「問題はあなたの〜です」等、相手を名指しで断罪し「保存して見返して」と促す） | 反応するのは共感して発散したい層で、読者と違う。/notekaigi（2026-09-16）で不採用確定 |
| 恋愛インフルエンサー型の断定・攻撃口調 | 「責められない分析」ブランドと非一貫 |

**未解決設計の原則**：「なぜそうなるか」か「どうすれば変えられるか」のどちらか一方を意図的に書かない。両方書くと共感で消費されて保存されず、空白にした問いが有料記事への自然な橋渡しになる。無料の投稿で渡すのは入口の一歩まで。タイプ別の具体設計図・体系的な出口は有料記事側に残す。

# ▼ 投稿ファイルの書き方（一時ファイル・`posts_x.txt` 共通）

```
【10/5 08:00】型ラベル／MBTI(INFP)
--------------------------------
（本文）
--------------------------------
自己リプライ（続き型）：（自己リプライ本文。ないときはこの行ごと書かない）
自己リプライ2（URL事後型・記事②・パターンB'）：（URL誘導の文）
→ https://note.com/...
```

- 見出し：`【M/D HH:MM】型ラベル／FW`。FWは `MBTI(タイプ)`・`MBTI(Nタイプ横断)`・`ラブタイプ(タイプ)`・`タイプなし`（検品の内訳集計とシートの型・FW列に使われる）
- 本文の前後は `--------------------------------`（ハイフン10個以上）で囲む。複数投稿は、空行を挟んで見出しから続けて書く
- 型ラベルに「続き型」「URL事後型」「リスト型」を含めると、変換ツールがリプライ欠落を警告する
- 完結型にURL誘導を付けるときは、`自己リプライ（URL事後型・記事◯・パターン◯）：` ＋ `→ URL`

# ▼ 自己リプライの仕組み（Threads）

| 役割 | 構造 |
|---|---|
| 完結型 | 本文だけで完結。リプライなし |
| 続き型 | 本文の最後の一文を読点（「、」）で文法的に途切れさせ、自己リプライがそのまま完成させる。「続きはリプ欄で」のような予告は禁止。URLなし。一部のタイプしか載せないときは「残り」と書かず、「続きの○タイプは、」にする |
| URL事後型 | 本文とは別に、URL付きの自己リプライを**本編投稿から約2時間あけて**送る（`threads_scheduler.gs` の `postDelayedUrlReplies()` が自動処理） |
| 続き型＋URL誘導（`自己リプライ2`） | 自己リプライ枠が本文の続きで埋まっている投稿向け。2本目は「1本目への返信」として2時間後に自動投稿される |

- `qa_post.py` は `自己リプライ2` を別に検品する。変換ツールが6列目（URL自己リプライ）へ振り分け、投入ツールがシートの列Jに書く。
- **自己リプライは即コンテンツ化**：「〜の話を書いています」のようなテザー型は禁止。続き型の自己リプライは、1段目から補足の具体例・見分け方・比較を出す。
- **URL誘導リプライ**：1〜2行＋URLで完結。**平たい文**（`rules/style_0930.md` 7）。文末は丁寧語。情景を作った表現・広告文句（「必見」「保存推奨」等）・同一フレーズの使い回しは禁止。
- **文字数（ハード制約）**：本文・自己リプライとも、Threads APIの上限は各500字（超えると投稿時に失敗する）。収まらない型は、圧縮せず続き型として自己リプライへ分割する。

# ▼ X専用ルール（運用再開時のみ）

- **文字数**：140字以内（超過はERROR）／**URL**：本文に入れない（自己リプライへ）／ハッシュタグなし

# ▼ Threads専用ルール

- **文字数**：本文の目安は**100〜350字**（短い投稿のほうが返信を集めていた〈2026-10-17〉。目安を外れるとWARN）、自己リプライの目安は80〜150字（URL誘導は対象外）。ハード上限は500字
- **URL**：新規記事公開日のみ本文末尾可。それ以外は自己リプライ
- **タイプ名**：1行目に置いてよい。1行目は「場面＋何が分かるか」を優先する（`rules/style_0930.md` 6）
- **他者リプライ**：他者投稿へのリプライは高ROI。1〜2行の短文のみ。生成は `/reply` スキル

# ▼ Note誘導

- **誘導は週1〜3本**（最低1本は露出を作る・最大3本）。付けるのは、相性のよい記事（`cta_templates.md` の「相性の良い本文の傾向」）がある投稿だけ。**見られやすい形（番号リスト・続き型）に絞り、付ける日は離して**、毎回付けない。人が運用していると分かる間隔にする。
- **記事ローテーション**：迷う場合は、直近4週間でURL誘導していない有料記事（②③⑤）を優先する。目的は均等配分ではなく「露出ゼロを作らない」こと。直近の誘導は `show_queue_recent.py --full` の自己リプライで確認する。
- 誘導文は**平たい文**（`cta_templates.md` のパターンB'）。URL付きの投稿は、出口を書ききらない（未解決設計）を優先し、結果をURLなしと比べて記録する。
- 型C'（委ね切り型）・型D は購買意図が高くない読者が多いため、誘導には使わない。
- Threadsのプロフィールリンクは無料記事⑧、固定投稿（自己開示＋⑧への案内）を設置済み。プロフィールは「一番冷たい入口」なので無料記事で受け、投稿内のCTAは温まった読者向けと使い分ける。
- 見直しのタイミング：有料記事フラッグシップ着手条件（`mbticode_strategy.md`：980〜1,480円帯で販売実績2件）が満たされたとき、または⑧よりテーマが合う無料記事が出たとき。

# ▼ 外部リプライ自動応答（完全自動）

自分の投稿に他者から付いたリプライへ、返信文を自動生成し自動投稿する仕組み。**投稿前レビューなしの完全自動**（リプライ自体がほぼ発生していないためリスク許容。品質が不安定なら見直す）。

**パイプライン**（`tools/threads_scheduler.gs` 実装済み）：
1. `detectExternalReplies()`（10分間隔）：外部リプライを検知し「外部リプライキュー」シートへ未処理として記録
2. `syncReplyCandidatesToGitHub()`（10分間隔）：未処理分をGitHub（`tools/_reply_candidates.json`）へ同期
3. **返信文生成ルーティン**（クラウド側cronの最小間隔＝1時間）：`_reply_candidates.json` を読み、下記ルールで返信文を生成し `tools/_pending_reply_posts.json` へ書き込みコミット
4. `pullGeneratedRepliesFromGitHub()`（1時間間隔）：生成された返信文を実際に投稿し、キューを更新

**返信文生成ルーティンが必ず守るルール**：
- 文体・判断基準は `rules/feedback_mbticode_reply_style.md` が唯一の正
- **タイミング判断**：相手の意図が「質問」か「考察・共感の共有」かを見極める。事実訂正が必要なケースは即答モードにせず、慎重な言い回しにする
- **捏造禁止**：`personal_data.md` にない体験を「わかります」等で語らない。部分的な共通点のみなら「INTPも似たのがあって」と正直に表現する
- 生成に迷う・攻撃的・センシティブな内容のリプライは、返信文を作らず `_pending_reply_posts.json` に含めない（未処理のまま残し、ユーザーが手動確認する）
- コミット前に本ルールに沿っているか自己チェックする（投稿前に人が見ないため、この自己チェックが唯一のゲート）

# ▼ 型カタログ（`/reply` の「横展開の判定」用）

`/reply` Step2 は、既存の型と重複していないかをこの表だけで確認する。新しい型を追加したらこの表にも1行足す。

| 型名 | 構造一言 | 媒体 |
|---|---|---|
| 型A（シーン共感） | 行動シーン共感→構造解説→タイプ名→他者投影 | X/Threads |
| 型B（解釈転換） | 観察／問いかけ／独り言／従来型の4冒頭パターン | X/Threads |
| 型C（問い＋自答） | 問いを立てて自分で答える | X/Threads |
| 型C'（委ね切り型） | シーン→自分の反応描写→読者に完全に委ねる | Threads |
| 型α（2行逆転） | A行：直感に反する命題／B行：さらに裏切る命題 | X限定 |
