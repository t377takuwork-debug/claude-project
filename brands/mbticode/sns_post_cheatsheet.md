# ▼ 生成ワークフロー（唯一の正・毎回この順序で実行）

**Step 1. 資料を読む（内容の正確性のため必須）**
- 投稿で**タイプの話をする場合は、書く前に必ず該当する資料を読む**：
  - MBTI → `reference/mbti_quick_ref.md`
  - ラブタイプ → `reference/lovetype_sns_ref.txt`（詳細が要るときだけ `reference/ラブタイプ各キャラクター傾向まとめ.txt`）
  - DSKB → `reference/dskb_quick_ref.md`（FWとしては廃止済み。使わない）
  - 恋愛系トレンドワード（一途・執着・独占・ヤンデレ・サレ女等）を使う → `reference/trend_words_bank.md`
- 「▼ 内容の正確性」のチェックを、生成のあいだ守る。

**Step 2. 相談（チャット）→ ユーザーOKを取る**
- テーマ・型・タイプの決め方は保留中。案を出して、ユーザーに決めてもらう。
- **案は `analysis/patterns.md`（基礎分析のパターン候補）を参考に作る**。案ごとに「どのパターンに沿っているか／新しく試す変更か」を1行添える。確度が低いパターンは、1つずつ変えて試す。同じパターンの投稿が続きすぎないか、直近のキュー（`show_queue_recent.py`）と見比べて確認する。パターンを型の比率などの決まりごとへ反映するのは、ユーザーが指示したときだけ。
- **ネタの重複確認**：Threadsは `python brands/mbticode/tools/show_queue_recent.py`（直近7日＋未来分の一覧。中身まで見るときは `--full`）、Xは `posts_x.txt` の残存分で行う。
- 同じタイプ・同じ主張の骨子を、直近7日＋今回の分で繰り返さない（言い方を変えただけの焼き直しもNG）。

**Step 3. 生成して検品する（チャット出力は最小限）**
- バッチを**一時ファイル** `posts/_batch_MMDD.txt` に書く（形式は「▼ 投稿ファイルの書き方」）。
- `python brands/tools/qa_post.py brands/mbticode/posts/_batch_MMDD.txt --account mbticode --platform threads` で **ERROR 0件・exit=0**（Xは `--platform x`）。
- 文体系の検品は保留中のためWARN扱い。**WARNは削除・自己判断で潰さず、報告に全文転記する**（人間が判断する）。
- **「自分のネタ」（外部の元ネタを参考にしたネタ）から作った投稿は、保存・投入の前に類似チェックを行う**（型を再現せず「反響を生む要素」を取り入れる。型・テーマ・タイプのうち元ネタと一致するのは最大1つ）：元ネタの核と自分の核を1行ずつ書いて着想の近さを判定（中は書き直す・高は使わない）＋`python brands/tools/check_similarity.py <一時ファイル> --sources <元ネタの本文の一時ファイル>`（10字以上はWARN・20字以上はERROR）。詳しくは `/mbticode-neta` の「類似チェック」
- 問題がある場合のみチャットで報告する（同じ指摘への修正は2回まで）。
- 確定前の壁打ちが必要な場合（新しい型の試験など）は `/post-review` を通す。

**Step 4. 保存**
- **Threads**：`python brands/mbticode/tools/threads_txt_to_csv.py <バッチ開始日> --src brands/mbticode/posts/_batch_MMDD.txt` でCSVを作り、`python brands/mbticode/tools/push_threads_queue.py <csv>` でシートへ投入する（過去時刻・重複は自動スキップ）。手作業のパース・シートの手編集は禁止。
- **X**：`posts_x.txt` に対象分を末尾追記する。7日より古い分は `posts/archive/` へ移す。
- CTA（URL誘導）が要る投稿は `posts/cta_templates.md` の使い方に従って選び、本文とセットで書く。
- 投入が成功したら、一時ファイルは削除してよい（正はシート）。

**Step 5. シートで確認する**
- `python brands/mbticode/tools/show_queue_recent.py --days 0` で、今回入れた行がキューに並んでいることを確認する。
- `python brands/mbticode/tools/check_queue_coverage.py` でキューの残り日数を確認する。
- 週次クラウドルーティン産のバッチは `_pending_batch.json` → `apply_pending_batch.py` 経由（手順は同スクリプトのdocstring参照）。

**Step 6. 完了報告**
- qa_post.pyの結果（ERROR/WARN件数・exit値）・シートに入った行数と日時・Xの保存先を1〜3行で報告する。

# ▼ 内容の正確性（`reference/` を踏まえた提案にするための確認）

生成のあいだ、次を確認する（意味の判断が要る項目。機械では見られない）。
- [ ] タイプに触れる投稿は、該当する `reference/` の資料を読んで書いた
- [ ] 本文の主張が、資料に書かれた特性から自然に導ける（資料にない特性づけ・架空の根拠はNG）
- [ ] 「なぜこのタイプにこのパターンが出やすいか」を1行で言える
- [ ] タイプ名は「アルファベット＋（日本語名）」で、日本語名はMBTI公式の表記（INFP（仲介者型）／ESFJ（領事官型）／ISFP（冒険家型）／ENFJ（主人公型）／ISFJ（擁護者型）／ENFP（運動家型）／INTP（論理学者型）等）
- [ ] MBTIの軸の名前を取り違えていない（N＝直観、S＝感覚）。他アカウントの投稿をそのまま転用しない
- [ ] 実在人物を想起させる断定、特定の人やタイプを傷つける決めつけ、断定的な統計（「〇割は〜」）を書いていない（`brands/CLAUDE.md` 絶対遵守ルール3）
- [ ] 発信者の体験を匂わせる場合は `personal_data.md` の範囲内（体験の捏造は禁止）。タイプ言及なしの投稿でも根拠のない一般論を書かない

# ▼ 採用しない型

| 型 | 排除理由 |
|---|---|
| 攻撃的ラベリング型（「異常者」等／「〜なだけだよ」と決めつけて閉じるキャラ付け含む） | 炎上リスク・ブランドと矛盾 |
| 議論誘発型（「〇〇って偏見だよね」系） | リプライは多いが保存率が極低く、転換率ゼロ |
| エンタメ消費型（DSKBの笑い文脈） | 保存されず有料記事への動線にならない |
| タイプ主語の断定的愚痴・お説教型（「F型は〜」「ISFPは〜」等で名指し批判） | 「責められない分析」と矛盾。数値が大きくても採用しない |
| 断罪型（「問題はあなたの〜です」等、相手を名指しで断罪し「保存して見返して」と促す） | 反応するのは共感して発散したい層で、読者と違う。/notekaigi（2026-09-16）で不採用確定 |
| 恋愛インフルエンサー型の断定・攻撃口調 | 「責められない分析」ブランドと非一貫 |

**未解決設計の原則**：「なぜそうなるか」か「どうすれば変えられるか」のどちらか一方を意図的に書かない。両方書くと共感で消費されて保存されず、空白にした問いが有料記事への自然な橋渡しになる。無料の投稿で渡すのは入口の一歩まで。タイプ別の具体設計図・体系的な出口は有料記事側に残す。

# ▼ 投稿ファイルの書き方（一時ファイル・`posts_x.txt` 共通）

```
【10/5 08:00】型A・完結型／MBTI(INFP)
--------------------------------
（本文）
--------------------------------
自己リプライ（続き型）：（自己リプライ本文。ないときはこの行ごと書かない）
```

- 見出し：`【M/D HH:MM】型ラベル／FW`。FWは `MBTI(タイプ)`・`ラブタイプ(タイプ)`・`タイプなし` のいずれか（検品の内訳集計とシートの型・FW列に使われる）
- 本文の前後は `--------------------------------`（ハイフン10個以上）で囲む
- 複数投稿は、空行を挟んで見出しから続けて書く
- 型ラベルに「続き型」「URL事後型」「リスト型」を含めると、変換ツールがリプライ欠落を警告する

# ▼ 自己リプライの仕組み（Threads）

| 役割 | 構造 |
|---|---|
| 完結型 | 本文だけで完結。リプライなし |
| 続き型 | 本文の最後の一文を読点（「、」）で文法的に途切れさせ、自己リプライがそのまま完成させる。「続きはリプ欄で」のような予告メタ発言は禁止。URLなし |
| URL事後型 | 本文とは別に、URL付きの自己リプライを**本編投稿から約2時間あけて**送る（`threads_scheduler.gs`の`postDelayedUrlReplies()`が自動処理） |
| 続き型＋URL誘導（`自己リプライ2`） | 自己リプライ枠が本文の続きで埋まっている投稿（続き型のリスト型など）向け。`自己リプライ（続き型…）：`に続けて`自己リプライ2（URL事後型・記事◯パターン◯）：`で始め、`→ URL`行を含める。2本目は「1本目への返信」として2時間後に自動投稿される。型ラベルは「続き型・URL事後型」と併記 |

- `qa_post.py` は `自己リプライ2` を1本目と別に検品する（字数・禁止表現・`cta_templates.md` との突き合わせ）。変換ツールが6列目（URL自己リプライ）へ振り分け、投入ツールがシートの列Jに書く。
- **自己リプライは即コンテンツ化**：「〜の話を書いています」のようなテザー型は禁止。1段目から補足の具体例・見分け方・比較を出す。
- **URL誘導リプライ**：1〜2行＋URLで完結（水増し禁止）。文末は丁寧語（ですます調）で全文統一し、「続きに置いてる。」等の機械的な予告フレーズ・広告文句・同一フレーズの使い回しは禁止（実例は `cta_templates.md`。既存パターンが旧文体のままの場合は書き直してから使う）。
- **文字数（ハード制約）**：本文・自己リプライとも、Threads APIの上限は各500字（超えると投稿時に必ず失敗する。`th-length-api-limit`等でERROR）。500字に収まらない型は、圧縮せず続き型として自己リプライへ分割する。

# ▼ X専用ルール

- **文字数**：140字以内（超過はERROR）／**URL**：本文に入れない（自己リプライへ）／ハッシュタグなし
- **ラブタイプのアルファベット**（FCPE等）：140字の制約上、自己リプライに回してもよい
- **役割**：X＝「扉を叩く」型。Threadsの圧縮版にしない。金言フレーズ1本で完結する別コンテンツとして設計する
- **自己リプライ（X）**：URL誘導型のみ。反応が来た投稿に後から追加（新規記事公開日のみ投稿直後に追加可）。1〜2行の誘導文＋URL
- **引用ポスト**：引用元は `posts/quote_target_list.md` から選ぶ（フォロワー5,000人以上を優先）。生成は `/reply` スキル（種別：引用RT）

# ▼ Threads専用ルール

- **文字数**：本文の目安は200〜350字、自己リプライの目安は80〜150字（目安を外れるとWARN。ハード上限は上の500字）
- **URL**：新規記事公開日のみ本文末尾可。それ以外は自己リプライ
- **体験匂わせ**：冒頭または本文2〜3行目に入れる（`personal_data.md` の範囲内）
- **タイプ名**：書き出しに置かず、中盤以降に着地させる
- **他者リプライ**：他者投稿へのリプライは高ROI。1〜2行の短文のみ。生成は `/reply` スキル

# ▼ Note誘導

## 週1回の計画的Note誘導枠

- 反応の大小に関わらず、**週1本は能動的にNote誘導CTAを配置する**（曜日・時間帯は固定しない）
- 誘導先は `cta_templates.md` の「相性の良い本文の傾向」を見て本文テーマと合わせる
- **記事ローテーション**：迷う場合は、直近4週間でURL誘導していない有料記事（②③⑤）を優先する。目的は均等配分ではなく「露出ゼロを作らない」こと。直近の誘導は `show_queue_recent.py --full` の自己リプライで確認する
- 型C'（委ね切り型）・型D は購買意図が高くない読者が多いため、この枠には使わない（完結型・続き型を使う）
- **URL誘導は週1〜2本に限る**（2026-09-29決定）。URL付きにするのは、CTAの「相性の良い本文の傾向」に合う投稿だけ。URL付きの投稿は、出口を書ききらない（未解決設計）を優先し、結果をURLなしと比べて記録する。続き型は、1バッチに2〜3本を試験的に入れる
- フォロワーが増え、受動誘導だけで週1回以上の機会が生まれるようになったら、この枠の要否を再判断する

## 誘導比率・プロフィールリンク

- 有料記事②③⑤への誘導CTAは「露出ゼロを作らない」の通常ローテーションで行い、頻度を下げる特別扱いはしない（フォロワー数のゲートは2026-09-17に廃止済み）
- Threadsのプロフィールリンクは無料記事⑧、固定投稿（自己開示＋⑧への案内）を設置済み（2026-09-19）。プロフィールは全訪問者が見る「一番冷たい入口」なので無料記事で受け、投稿内のCTAは温まった読者向けと使い分ける
- 見直しのタイミング：有料記事フラッグシップ着手条件（`mbticode_strategy.md`：980〜1,480円帯で販売実績2件）が満たされたとき、または⑧よりテーマが合う無料記事が出たとき

# ▼ 外部リプライ自動応答（完全自動）

自分の投稿に他者から付いたリプライへ、返信文を自動生成し自動投稿する仕組み。**投稿前レビューなしの完全自動**（リプライ自体がほぼ発生していないためリスク許容。品質が不安定なら見直す）。

**パイプライン**（`tools/threads_scheduler.gs`実装済み）：
1. `detectExternalReplies()`（10分間隔）：外部リプライを検知し「外部リプライキュー」シートへ未処理として記録
2. `syncReplyCandidatesToGitHub()`（10分間隔）：未処理分をGitHub（`tools/_reply_candidates.json`）へ同期
3. **返信文生成ルーティン**（クラウド側cronの最小間隔＝1時間）：`_reply_candidates.json`を読み、下記ルールで返信文を生成し`tools/_pending_reply_posts.json`へ書き込みコミット
4. `pullGeneratedRepliesFromGitHub()`（1時間間隔）：生成された返信文を実際に投稿し、キューを更新

**返信文生成ルーティンが必ず守るルール**：
- 文体・判断基準は`rules/feedback_mbticode_reply_style.md`が唯一の正
- **タイミング判断**：相手の意図が「質問」か「考察・共感の共有」かを見極める。事実訂正が必要なケースは即答モードにせず、慎重な言い回しにする
- **捏造禁止**：`personal_data.md`にない体験を「わかります」等で語らない。部分的な共通点のみなら「INTPも似たのがあって」と正直に表現する
- 生成に迷う・攻撃的・センシティブな内容のリプライは、返信文を作らず`_pending_reply_posts.json`に含めない（未処理のまま残し、ユーザーが手動確認する）
- コミット前に本ルールに沿っているか自己チェックする（投稿前に人が見ないため、この自己チェックが唯一のゲート）

# ▼ 型カタログ（`/reply` の「横展開の判定」用・作り直しまで参照用）

`/reply` Step2 は、既存の型と重複していないかをこの表だけで確認する。新しい型を追加したらこの表にも1行足す。型の詳しい定義は退避先ファイルにある。

| 型名 | 構造一言 | 媒体 |
|---|---|---|
| 型A（シーン共感） | 行動シーン共感→構造解説→タイプ名→他者投影 | X/Threads |
| 型B（解釈転換） | 観察／問いかけ／独り言／従来型の4冒頭パターン | X/Threads |
| 型C（問い＋自答） | 問いを立てて自分で答える | X/Threads |
| 型C'（委ね切り型） | シーン→自分の反応描写→読者に完全に委ねる | Threads |
| 型α（2行逆転） | A行：直感に反する命題／B行：さらに裏切る命題 | X限定 |
| 二つの温度型 | 相反する感情が矛盾せず同時に存在する構造 | Threads |
| リスト型 | 箇条書き・後で確認したくなる構造（見分け方二択／全16タイプ矛盾一言／ラブタイプ9タイプ数字を含む） | Threads |
| 非対称理解型 | 一方向にしか理解できない関係性を構造化して命名する（型Bのサブタイプ） | Threads |
| ミニマル観察型 | 2〜3行・逆説を一言で言い切って止める（型Bのサブタイプ） | Threads |
| コメント参加依頼型 | 読者に「ひとつだけ教えてください」と具体的な行動を依頼する | Threads |
| 型D（DSKB） | **廃止** | ― |
