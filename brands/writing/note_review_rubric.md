# note_review_rubric.md — Note記事 審査ルーブリック（note-ai-reviewer の唯一の採点基準）

> **用途**：本文完成後・ユーザーへ提案する前に、`note-ai-reviewer` がこの表で採点する。PASS が出るまで本文はユーザーに提示しない。
> **適用**：s4lv／MBTICODE／vivant（junk_juice は対象外）。
> **定義の正**：このファイルは「何をどの重さで見るか」だけを決める。各項目の定義・言い換え表は `writing_tone.md`（文体）・`writing_core.md` AI臭さ除去章＋句読点（定型表現・重複・制作側用語）・`writing_note_structure.md`（構成）・各アカウント上書き元が正。ここに定義を複製しない。
> **成立**：2026-09-04（Step 2）。`docs/note_article_asset_inventory.md` 参照。

---

## 0. 判定の枠組み

| 重大度 | 意味 | 提案可否 |
|---|---|---|
| **BLOCK** | 読者に出せない。事実・規約・機械ERROR・AIっぽさの決定的な兆候 | 不可。修正必須 |
| **FIX** | 出せるが質を落としている。writing_tone／AI臭さ章に明確に反する | 不可。修正してから（最大2巡） |
| **NOTE** | 判断が分かれる・好みの範囲・次回への示唆 | 可。指摘を添えて提案 |

- **PASS ＝ BLOCK 0件 かつ FIX 0件**。NOTE は残ってよい
- FAIL → 司令塔が指摘に沿って修正し再審査。**同じ指摘への修正は2巡まで**。2巡後に残る FIX は、現状・試したこと・残る理由を添えてユーザー判断に回す（黙って通さない・黙って落とし続けない）
- 機械QA（`qa_article.py`）で ERROR が出た場合は即 FAIL。LLM審査は行わない（機械で落ちるものを再走査しない）
- WARN は審査員が1件ずつ「要修正（FIX）／許容（NOTE）」に振り分ける。許容には理由を書く（例：プロンプト枠内の「ください」連続は許容）

## 1. 審査員の態度（忖度禁止）

- 褒めから入らない。「全体的に良い」「読みやすい」等の総括で済ませない
- すべての指摘に**行番号と本文の引用**を付ける。引用できない指摘は出さない
- ルーブリック外の好みで指摘しない。根拠は必ず writing_tone／writing_core／note_structure／アカウント上書き元のどれかの節を示す
- 見つからなければ「該当なし」と書く。無理に指摘を作らない
- **本文は書き換えない**。直し方は1文で示す（全文リライト案は出さない。書くのは司令塔の仕事）
- 1回目は評価せず、初見の読者として最後まで通読する。2回目に採点する

## 2. 採点項目

各項目の「見るもの」は要点のみ。定義は右列の正を読む。

### A. 機械QA（`brands/tools/qa_article.py`）
| 見るもの | 重大度 | 正 |
|---|---|---|
| ERROR が1件でもある | BLOCK（即FAIL） | qa_article.py 層1 |
| WARN の各件を要修正／許容に振り分ける | 件ごとに FIX／NOTE | 各層の出典 |

### B. AI定型・構文の薄さ
| 見るもの | 重大度 | 正 |
|---|---|---|
| 要約フレーズ・抽象総括・予防線・説教口調（機械が拾い切れない言い換え形を含む） | FIX | writing_core AI臭さ章／writing_tone 1-1 |
| ヘッジの二重掛け（「たぶん〜んじゃないかと思う」）、「……＋独立した相槌」 | FIX | writing_tone 1-2・1-4 |
| 「〜の域を出ません」等の定型ヘッジ、時間経過を演出する情景、取ってつけた接続語、自問自答の締めの多用 | FIX | writing_tone 1-4 |
| 訳語調・硬い漢語・比喩の常套句（ものさし等）、文頭「これ、」、読者向け「渡します」 | FIX | writing_tone 1-1 |

### C. 平均的回答になっていないか（独自性）
| 見るもの | 重大度 | 正 |
|---|---|---|
| **誰が書いても同じ内容**になっていないか。検索上位の要約で置き換え可能な段落がないか | BLOCK（記事の核がこれなら）／FIX（一部の段落なら） | writing_note_structure「ニッチ義務化」／writing_core 5大ルール5 |
| 実測値・一次情報・著者の判断の跡（外した理由・迷った経緯）が本文にあるか | FIX | writing_core 親近感8手法／note_asset_check「一次情報」 |
| 「その発想はなかった」と言える視点の転換・命名・区別が1つ以上あるか | FIX | writing_note_structure H2設計 |
| 制作側の分析用語がそのまま本文に出ていないか | FIX | writing_core AI臭さ章・qa層4 |

### D. 文体・トーン（アカウント上書きを適用）
| 見るもの | 重大度 | 正 |
|---|---|---|
| 口語化：じゃない／だから／禁止語（1-1の一覧） | FIX | writing_tone 1-1＋2章 |
| **段落末の語尾**が揃っていないか（段落の切れ目だけ拾い読みして判定。文中の散らばりは免罪符にしない）。**閾値：同一語尾（末尾2字）が3段落連続＝FIX、2連続＝NOTE**（2026-09-04・審査の揺れを固定） | FIX／NOTE | writing_tone 1-2 |
| 「〜だ。」への逃げ込み、「〜と思います」「〜ですね」「〜しましょう」（アカウント上書きで可のものは除く） | FIX | writing_tone 1-2・2章 |
| 断言のメリハリ：核心は言い切り、痛みはやわらかく、が同居しているか。全部やわらかい／全部言い切りは不可 | FIX | writing_tone 1-7 |
| アカウントの人格から外れていないか（s4lv＝謙虚な職人・命令口調不可／MBTICODE＝メンター・設計官／vivant＝観察者・断定回避） | FIX | writing_tone 2章＋各上書き元 |

### E. 段落・余白・リズム
| 見るもの | 重大度 | 正 |
|---|---|---|
| 段落が2〜4文の塊になっているか。1文ずつの改行が続いていないか／3〜4文超の塊が続いていないか | FIX | writing_tone 1-3 |
| 全角スペース行の一拍が節目だけに置かれているか（多すぎ＝間延び／なし＝密集）。二重改行で余白を作ろうとしていないか | FIX | writing_tone 1-3 |
| リズム：短い断定文・体言止め・相反2文の塊が使われ、淡々と流れていないか | FIX | writing_tone 1-4 |

### F. 冒頭フック・ベネフィット
| 見るもの | 重大度 | 正 |
|---|---|---|
| 最初の300字に痛み／ベネフィット／フックが揃っているか | BLOCK（ベネフィット欠落）／FIX | writing_note_structure 導入3要素 |
| ベネフィットが「〜できるようになる」の一文で言い切られているか（作業宣言・列挙止まりは不可） | FIX | writing_tone 1-6 |
| フックが手垢のついた情景・伝聞（「〜という声も」）・読者反応の決めつけになっていないか | FIX | writing_tone 1-5・1-6 |
| 導入の型・締めの語尾が直近公開記事と同じでないか（同アカウント `articles/published/` 直近2本と比較） | FIX | writing_tone 1-6・1-10 |

### G. 親しみ・寄り添い
| 見るもの | 重大度 | 正 |
|---|---|---|
| 読者の内心の代弁があるか。その直後に寄り添い一言があるか（過剰・ハグ調は逆にFIX） | FIX | writing_tone 1-5 |
| 読者の反応・記憶・心理を決めつける表現（「〜た方も多いはず」「思わず声が出た」）がないか | FIX | writing_tone 1-5 |
| 「正直に言うと」等の開示フレーズが2回以上ないか | FIX | writing_tone 1-5 |
| 責める書き方（「あなたが悪い」に読める断定）になっていないか | FIX | writing_tone 1-5／MBTICODE persona「責められない分析」 |

### H. 既視感
| 見るもの | 重大度 | 正 |
|---|---|---|
| 見本ファイル（`examples_*.md`）・既存記事の言い回しを流用していないか（qa層5の20字一致に加え、型・比喩・締めの構造レベルで） | FIX | writing_tone 1-10 |
| 記事内で同じ主張を言い直していないか（qa層6に加え、語彙が違う言い直しも） | FIX | writing_tone 1-10 |

### I. 事実・前提・規約
| 見るもの | 重大度 | 正 |
|---|---|---|
| `personal_data.md` にない実績・数字・体験がないか（vivant は content_policy：出典不明の統計・実体験と誤認させる一人称） | BLOCK | brands/CLAUDE.md 捏造禁止／vivant content_policy |
| Note規約（性的描写・断定的統計・特定個人） | BLOCK | brands/CLAUDE.md |
| 開示NG項目（番組名・ジャンル特定情報等）が直接・間接に漏れていないか | BLOCK | 各 personal_data 開示ルール |
| 制作順序（キーワード＋読者像→タイトル→構成→本文）を誤認させる記述、時系列の逆転した根拠 | FIX | writing_tone 1-11／vivant content_policy |
| 「〜と判明」と書いてよい確度か（報道・SNS反応を確定事実として書いていないか） | FIX | vivant content_policy／メモリ media_confirmed_may_be_suspicion |

### J. 構造・導線（軽く確認。詳細は各スキルのチェックリストが正）
| 見るもの | 重大度 | 正 |
|---|---|---|
| H2直下のH3が1本だけ、2,000字超で見出しなし | FIX | qa構造・s4lv process |
| N（絞り込み）→1つのCTA→あえての隙、の順が崩れていないか（有料・MBTICODEは必須） | FIX | writing_note_structure 結論／mbticode_tone |

| 引用枠内の番号リスト・`- `・MDリンク等、Note貼り付けで崩れる記法 | FIX | writing_tone 1-9・qa層3 |

## 3. 出力フォーマット（固定・この形以外で返さない）

```
## 審査結果: PASS
（または）
## 審査結果: FAIL（BLOCK n件／FIX n件／NOTE n件）

対象: <パス>　アカウント: <s4lv|MBTICODE|vivant>　種別: <無料|有料>　本文: <n>字
機械QA: ERROR <n> / WARN <n>（WARNの振り分け: FIX <n> / NOTE <n>）

| # | 重大度 | 区分 | 行 | 指摘（本文引用） | 直し方（1文） | 根拠 |
|---|---|---|---|---|---|---|
| 1 | BLOCK | I | L43 | 「…」 | … | writing_tone 1-11 |
| 2 | FIX | D | L15,L27,L39 | 段落末が「〜です。」×3連続 | … | writing_tone 1-2 |
（BLOCK→FIX→NOTE の順・同重大度内は行番号順）

### 総評（3行以内）
- 一番効く修正: #n（理由1文）
- 良い点: 1つだけ、行番号付き（無ければ「特記なし」）
- 次回への示唆: 1文（無ければ省略）
```

- 見出し行の BLOCK／FIX／NOTE 件数は**表の行数**と一致させる（同種の指摘は1行にまとめ、行欄に該当行を列挙する）。WARN の振り分け件数は「機械QA」行に別途書く
- 指摘が0件の区分は表に出さない。全区分0件なら表を省略し「指摘なし」と書く
- 2巡目以降は「前回#nの対応: 解消／未解消（理由）」を表の前に1行ずつ書く

## 4. 更新ルール

- 項目の追加・重大度の変更は本ファイルを先に直し、`note-ai-reviewer.md` は参照するだけ（手順を再掲しない）
- 定義そのものの変更は `writing_tone.md` 等の正へ。本ファイルには書かない
- 審査で「ルーブリックにないが明らかにおかしい」が出たら、NOTE として指摘し、本ファイルへの追加を司令塔経由でユーザーに提案する（審査員が勝手に基準を増やさない）
