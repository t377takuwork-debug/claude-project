# STAR リライト用 資料①②リサーチ

`/star-rewrite` で資料①（または資料①②とも）が渡されなかった回に、本編リライトへ入る前に実行するリサーチ手順。

**このファイルを読むのは「資料が渡されなかった回」だけ。** 資料が渡された回は `star-rewrite.md` の「作業手順」1へ直行する（このファイルは読まない）。

完了条件：整形した資料①②を `tools/output/star_material.md` に保存し、チャットでユーザー承認を得ること。承認前に `star-rewrite.md` の作業手順へ進まない。

番組の固定情報（放送局・放送枠・公式サイト・MC・TVerシリーズURL・記事URL）は `star-rewrite.md`「番組基本情報（固定）」を正とする。ここで扱うのは毎回変わる情報だけ。

> **STAR は CDTV/Mステより資料集めが楽**：放送前に歌唱曲まで発表される回が多く、Billboard JAPAN が「フジテレビ『STAR』、M/DDは〇〇が登場」の定型ラインナップ記事を毎週出す（＝CDTVの THE FIRST TIMES まとめ記事に相当）。ただし固定URLではないので入口は Yahoo検索。

## 使用ソースと取得順（トークン節約のため最小構成・2026-09-09 実地テスト確定）

STARの調査で必要なのは **出演者・歌唱曲・ナビゲーター・放送内容（放送日／見どころ・特別企画）** だけ。放送枠は木曜 19:00〜20:00 固定なので調べない。下の主ソース2つでほぼ揃う。

| 優先 | ソース | 取得方法 | 役割 |
|---|---|---|---|
| 主① | Yahoo!ニュース検索 `https://news.yahoo.co.jp/search?p=STAR%20フジテレビ%20音楽番組&ei=utf-8` | WebFetch 1回 ✅ | 放送日ごとの記事一覧。次回放送回と直前回を報じる記事のURL特定、および『直近の放送回の特定』用の放送カレンダー。**クエリは `p=STAR フジテレビ 音楽番組` 固定**（`p=STAR` 単体だと映画・スポーツのSTARが大量に混ざる） |
| 主② | 主①で拾った**ラインナップ記事**（Billboard JAPAN「フジテレビ『STAR』、M/DDは〇〇が登場」を最優先。無ければ 音楽ナタリー／THE FIRST TIMES／モデルプレス／オリコンのYahooミラー） | WebFetch 1〜2回 ✅ | 放送日・全出演アーティスト・**各歌唱曲（判明分）**・ナビゲーター・タイアップ・特別企画の確定。**2媒体でクロスチェック** |

## 資料① リサーチ手順

1. **主① Yahoo検索を WebFetch。** プロンプトは「**フジテレビの木曜19時の音楽番組『STAR』の放送回に言及する記事だけを、放送日ごとに列挙（見出し・配信元・配信日時・記事URL）。映画・スポーツ等の別STARは除外。今日以降で最も近い次回放送回と、直近の過去放送回を報じる記事を明示。本文要約は不要。記事URLは `news.yahoo.co.jp/articles/...` 形式で**」と絞る（返り値を小さく＝トークン節約）。この一覧が「実際の放送カレンダー」になり、飛んだ週（夏季・年末など）の判定と『直近の放送回の特定』（下記）に使う。
2. **主② ラインナップ記事を WebFetch。** 主①の一覧から**次回放送回のラインナップ記事**を選ぶ（Billboard JAPAN の定型記事＞音楽ナタリー＞THE FIRST TIMES＞モデルプレス＞オリコン）。プロンプトは「**M月DD日放送のフジテレビ『STAR』について抽出：放送日／全出演アーティスト／各アーティストの歌唱曲（判明分は曲名を省略・要約せず全曲そのまま）／ナビゲーター／初披露・コラボ・特別企画・スペシャルステージ・メドレー等の見どころ／出演順・タイムテーブルの記載があればそれも。記事にない項目は『記載なし』。憶測で補わない**」。
3. **主①検索結果ページのサマリーに並ぶ出演者・曲名は単体では信用しない**（別日のゲストや密着記事の名前が混ざる。ナビゲーターも「グループ名・メンバー名」で表記ゆれする＝2026-09-09 の 9/10回で検索サマリー「モナキ・おヨネ」→本文で「ナビゲーターはおヨネ（モナキ）」と確定）。**必ず主②の記事本文で確定**する。1媒体で曲・出演者に欠落があれば、別媒体のミラー記事をもう1本だけ WebFetch してクロスチェックする。確定する抽出項目：
   - 放送日（放送枠は木19:00〜20:00 固定。特番で動く回だけ主②記事の記載を採る）
   - 全出演アーティスト
   - **各歌唱曲（判明分は曲名をそのまま。未発表なら「歌唱曲は後日発表」）**
   - **ナビゲーター**（毎回変わる。名義は「個人名（所属グループ）」で正規化。なし回は「なし」）／MC上垣皓太朗は固定なので確認不要
   - 初披露・テレビ初披露・コラボ・スペシャルステージ・メドレー・VTR企画・エンタメニュース関連の見どころ
   - **記事にない項目は「記載なし」とし、憶測で補わない。**
4. **曲のタイアップ・背景注記**（ドラマ主題歌・映画主題歌・新譜リード曲など）が記事にない曲は、**明らかな定番曲を除き最大2曲まで**、その曲を報じる記事を1本ずつ追いフェッチする。3曲以上不明なら追わず、該当カードは「◯◯を披露。」の最小記述にする。
5. 放送枠は木19:00〜20:00 で確定（`tools/output/programs.md` があれば Read して念のため照合）。**特別編成・時刻変更が主②記事に明記されている回だけ**、放送8日前以降に EPG（bangumi.org）で開始〜終了を確定する（**bangumi.org EPG は放送の約8日前からしか載らない**）。
6. 主①②で出演者・ナビゲーターが確認できない場合のみ、STAR公式サイトを Claude in Chrome で確認する。どうしても確認できなければ「出演者未発表」「ナビゲーター未発表」として扱い、その旨を承認提示に明示して `star-rewrite.md` のプレースホルダー運用（歌唱曲は後日発表 等）に切り替える。

> **資料①の完了条件**：全出演者が確定していること。歌唱曲は判明分がすべて拾えていること（未発表分は「後日発表」と明示）。ナビゲーターが確定していること（なし回は「なし」）。揃わない項目は承認提示時に赤字相当で明示する。

## 直近の放送回の特定（資料②の前に必須）

「先週の木曜」を機械計算しない（STARは毎週放送とは限らず、夏季・年末などで飛ぶ週がある。例：`draft_star.txt` は 8/13 の次が 9/3＝8/20・8/27 が飛んでいる）。次の手順で確定する。

1. `draft_star.txt` の**現在のメイン記事の放送日**を読む（＝前回リライトが用意した回）。これを直近放送回の第一候補とする。
2. その日付が **今日より前**なら、放送済み＝直近放送回の候補として確定に進む。今日以降（未放送）なら、直近放送回はアーカイブパネル（`star-rewrite.md` 手順9「STAR の実際の出演順【放送後更新】」）の日付。
3. 資料① 手順1（Yahoo検索）で得た「放送日ごとの記事一覧」を照合し、**候補より後・今日より前に別のSTAR放送日がないか**確認する。あれば最も新しいその日を直近放送回に更新する。
   - **この最初のYahoo検索結果が放送カレンダーの正**。ある週にSTARのラインナップ記事が1本も出ていなければ、その週は**休止**とみなす。`p=STAR フジテレビ ◯月◯日` のような日付入りの追加Yahoo検索は投げない（0件になりやすく、トークンの無駄。2026-09-09 の初回運用でこれを2回やって無駄にした）。休止の可能性は承認提示で「確信度：中（放送記事の不在から判断）」と1行添えれば足りる。
   - **休止週はカウントしない**：例）アーカイブパネル＝8/13、メイン記事＝9/3 で 8/20・8/27 に放送記事が無ければ、8/13 は 9/3 の「ちょうど1回前」として扱う（下の手順4）。
4. **アーカイブパネル（`star-rewrite.md` 手順9）の日付と照合**：
   - パネル日 ＝ 直近放送回 → 資料②は取得済み。**Grokをスキップ**しパネル内容を流用。
   - パネル日 ＝ 直近放送回のちょうど1回前（休止週は挟んでよい） → 正常。**Grokを実行**（下記）。
   - パネル日が実放送2回以上前（サイクルスキップ）→ 直近放送回でGrok実行。間の回は granular データ欠落として承認提示時に明示。
5. 上記で直近放送回が一意に確定できない場合は、**Grokを回さず「直近の放送回は◯月◯日で合っていますか」とユーザーに確認**してから進む。

> **`star-rewrite.md` 手順9（退避データ）との取り違え注意**：アーカイブパネルの現在の中身は**前々回**のデータで、今回の資料②で上書きされる。資料②＝ここで特定した**直近放送回**のデータ。前々回データは手順11で過去一覧へフルカード化する別物。混同しない（同種ミスの明文化）。

ここで確定した日付・（特番なら）特別編成名を、下のGrokプロンプトに実際に埋め込む。

## 資料② リサーチ手順（Grok 主 ＋ TVer 補正）

資料②は**直前回（＝上で特定した直近放送回）の実出演順・時間帯・SNS反応**。

- **組み立ての基準は Grok の X実況分析**（下記 A）。real-clock の時間帯（10分単位の割り振り）・SNS反応（投稿爆発の瞬間・Key_Insight）はGrokでしか取れない。
- **TVer（B）は「歌唱曲・登場順の裏取り」**。STARのエピソードJSON-LD `description` にアーティスト別セットリスト（`▼アーティスト「曲名」`）とナビゲーターが載る。**CDTVのような `【MM:SS】` タイムスタンプはない**（STARは44分の単一エピソード。Part分割なし）。`▼` の並びで大まかな出演順を相互確認し、曲名は正として Grok を見直す。
- 配信期間切れ等で B が取れない回は A だけで確定してよい。

**実行するのは**「直近の放送回の特定」手順4で **Grokを実行** と判定した場合のみ。スキップ判定ならこの節を飛ばし、アーカイブパネルの内容を資料②として使う。

**取得順は B（TVer）→ A（Grok）**。TVer は Chrome 2往復・数十秒で終わり、**その回の確定セットリスト（`▼アーティスト「曲名」`）とナビゲーター名**が取れる。これを下の A の Grokプロンプトの「出演アーティスト／既知の歌唱曲／ナビゲーター」欄にそのまま流し込めば、事前情報がドラフト由来より正確になり、Grok の検索精度も上がる。配信切れで TVer が取れない回だけ、事前情報をドラフトの現メイン記事から吸い出す（下表）。

**事前情報の抽出（TVerが取れなかった時のフォールバック。プロンプトへ差し込む。ドラフト上書き前に実施）**
「直近の放送回の特定」で確定した回のデータは、**上書き前の `draft_star.txt` の現メイン記事**から吸い出す。

| プロンプトの `[ ]` | 供給元（draft_star.txt 内） |
|---|---|
| 放送日 | 現メイン記事ヘッダー／H2タイムテーブルの日付 |
| 出演アーティスト | 手順7「出演者＆歌唱曲一覧」のラインナップカード群（JSON-LD `mentions` / BroadcastEvent `performer` でも可） |
| 既知の歌唱曲 | 同ラインナップの各行の曲名 |
| 主な企画・特徴／ナビゲーター | aside①「注目：」行・aside②の19:00 OP行・見どころ記述・「初披露」等のバッジ |

### A. Grok（基準データ）

**取得手順**（`env_grok_chrome_automation.md` の回避策に準拠。CDTV/Mステと共通）
1. `mcp__claude-in-chrome__tabs_context_mcp` で状態確認 → 新規タブ → `grok.com` へ navigate（ログイン済みChromeが前提。未ログイン・拡張不可なら下の「フォールバック」へ）。
2. ページ確認・要素操作は **`javascript_tool` のみ**（`screenshot`/`read_page`/`get_page_text` は常時通信SPAでタイムアウトするため使わない）。
3. 入力欄 `.tiptap.ProseMirror`（contenteditable）へ **`DataTransfer` ＋ `ClipboardEvent('paste')` を合成**してプロンプトを一括投入（`computer.type` は改行で誤送信される）。送信は `button[aria-label="送信"]` をクリック。
4. **完了検知**：送信後**最初のポーリングは40秒後**（検索フェーズだけで約50秒かかる。20秒×複数回の空振りを減らす）、以降は **1回あたり20秒**の `setTimeout` 待ちでポーリング（`javascript_tool` の1呼び出しは約30秒でCDPタイムアウトするので45秒待ちにしない）。`.message-bubble.relative.rounded-3xl` 最終要素の `innerText` で、**テキスト長が2回連続で不変** かつ 末尾が「`Ns 作業しました`／`N sources`」で終わっていれば完了。**上限7分**（1時間番組の通常回は約1.5分・ポーリング2〜3回）。
   **抽出の切り出しアンカー**：`innerText` 内に「`作業内容: Ns`」は検索ログ側に多数出るので indexOf で拾わない。**答え本文は最後の「`作業しました`」の直後から**始まる（`text.lastIndexOf('作業しました')` → 次の改行以降）。冒頭のツール検索ログ（「検索した𝕏 for …」の連続）はこれで捨てられる。採用するのは `全体傾向`／`全出演者＆全歌唱曲リスト`／時系列表／`アーティスト個別登場順まとめ`／補足。**時系列表が長くツール出力上限で切れる時は、ヘッダー＋表前半で1回・表後半＋まとめで1回の計2回まで**（それ以上の細切れ slice はしない。2026-09-09 初回運用で4回に膨らんだ）。
5. Grokプロンプト（1回・改行あり）。**`[ ]` は事前情報の抽出で得た実値に置換してから投入**（プレースホルダーのまま送らない）。ナビゲーターなし回は該当記述を削除：

### B. TVer（歌唱曲・登場順の裏取り）

STARのエピソードページのJSON-LD `description` に、**アーティスト別セットリスト（`▼アーティスト「曲名」…` 形式）とナビゲーター名**が載る。2026-09-09 の実地テストで 9/3回（`ep8j3ojgkg`）の `description` が
`今週のナビゲーターは、リリー・フランキー！ … ▼福山雅治「KISSして」「vs. ～知覚と快楽の螺旋～」「HELLO」 ▼King & Prince「So Honey」 ▼福山雅治「邂逅」 ▼中島健人「鬼事」 ▼＝LOVE「恋、はじめました。」 ▼スター初登場の瞬間！！大公開SP`
だった。**`▼` の並びは概ね放送の流れを反映**（福山がメドレー→後に単独曲、と2回登場している）。ただし `【MM:SS】` タイムスタンプは無いので、時間帯は Grok を正とし、TVer は「曲名の正確さ」と「大まかな出演順」の相互確認に使う。

**取得手順**（`tver.jp` は WebFetch 不可＝SPAで空シェル。Claude in Chrome のみ。**Chrome往復は series 1 ＋ episode 1 ＝計2回**に収める）
1. `https://tver.jp/series/sr1ksvsv1n` を navigate → 3.5秒待つ → `javascript_tool` で `a[href*="/episodes/"]` を集める。先頭付近に「44分 … 9月3日(木)放送分」の形で直近放送回のエピソード（`epXXXXXXXX`）が並ぶ。放送日ラベルで直近回を特定する。
2. そのエピソードページを navigate → 3.5秒待つ → JSON-LD抽出：
   ```js
   const jl=[...document.querySelectorAll('script[type="application/ld+json"]')].map(s=>{try{return JSON.parse(s.textContent)}catch(e){return null}}).filter(Boolean);
   const ep=jl.find(x=>x['@type']==='TVEpisode')||jl[0];
   ({name:ep&&ep.name, description:ep&&ep.description});
   ```
   `description` の `▼アーティスト「曲名」` 行を全部拾う。末尾の「スター初登場の瞬間！！大公開SP」等のVTR企画名も見どころとして拾う。冒頭の「今週のナビゲーターは、〇〇！」でナビゲーターも裏取りできる。
3. Grok結果（A）と突き合わせ、**曲名・曲数の食い違いがあれば TVer を正として Grok を見直す**。出演順が食い違うときは `▼` の並びと Grok の投稿クラスター順を両方併記し、承認提示で確信度「中」と明示。
4. 配信期間切れ（配信は次回放送までの約1週間）でエピソードが見当たらない場合は B をスキップし、A だけで確定する。ユーザーが概要文を手で貼ってくれた場合はそれを使う。

> **エピソードURLは毎回変わる**（`epXXXXXXXX` は回ごとに新規）。手順1のシリーズページから毎回たどる。シリーズURL `sr1ksvsv1n` は固定。

### C. マッピング（CLAUDE.md「資料② INPUT テンプレート」へ）

| Grok出力（＝A、Bで補正済み） | 資料②テンプレの行き先 |
|---|---|
| 時系列表の各行（時間帯・種別・詳細） | セットリスト表：時間帯／アーティスト／歌唱曲／備考（初披露・コラボ・メドレー等） |
| 表の後の「アーティスト個別登場順まとめ」 | セットリスト表の並び順を確定（○組目） |
| 企画コーナー（メドレー・スペシャルステージ）の位置 | 該当枠の備考に「メドレー：1.◯◯ 2.◯◯ …」で残す（順番推定困難な曲はその旨も） |
| 「最も投稿が爆発した瞬間」 | Key_Insight（なぜ伸びたか）＋ Top_Tweet（傾向の要約・引用不要） |
| ヘッダーの全出演者＆全歌唱曲リスト／全体傾向 | セットリスト表の網羅チェック／REPORTコメント欄 |

**Grok出力は X実況からの推定なので確信度を付す。「順番推定困難」「投稿確認に基づく推定」と明記された箇所はその旨を残す。Impression は使わない。**

### D. 仕上げクロスチェック

- 出演順は `draft_star.txt` の過去一覧（前々回）や資料①記事の発表順（＝五十音順が多い）と矛盾しないか1点だけクロスチェックし、矛盾があれば承認提示時に明示。
- 時間帯が10分単位でしか取れないのは正常。分刻みが無い組は「○組目」の順序だけ確定する。

**フォールバック**（Chrome拡張が使えない／Grokが応答しない）
アーカイブパネルの内容を資料②として流用し、Yahoo!ニュース検索 or Togetter で直近回のセットリスト記事を1本だけ WebFetch して出演順・歌唱曲の食い違いだけ検証する。SNS反応・時間帯は空欄のままにする。

## 組み立てと承認ゲート

1. 収集結果を CLAUDE.md の「資料② INPUT テンプレート」形式に整形し、あわせて資料①（放送日・出演者・歌唱曲・ナビゲーター・見どころ・特別企画）を箇条書きでまとめる。TVer補正（B）を使った場合は「TVer概要で曲名を裏取り／出演順は▼の並びで相互確認・時間帯はGrok」と一言添える。
2. 整形結果を `tools/output/star_material.md` に保存する（レビュー・修正用の記録）。
3. **整形した資料①②をチャットに提示し、ユーザーの承認（または修正）を得てから `star-rewrite.md` の作業手順1以降に着手する。** 憶測での補完箇所・確信度が低い項目・「記載なし」の項目は明示する（CLAUDE.md ガードレール準拠）。

## 精度・トークンガードレール

- **資料①は「主① Yahoo検索1回 → 主② ラインナップ記事1本」の2フェッチ基本。** 曲・出演者に欠落があった時だけクロスチェックのミラー1本を足す（最大3フェッチ）。
- **Yahoo検索フェッチは「放送日ごとに 見出し・配信元・配信日時・記事URL だけ。本文要約は不要」で固定**（緩いプロンプトだと数十記事の本文ダンプが返りトークンを浪費する）。
- **Yahoo検索クエリは `p=STAR フジテレビ 音楽番組` に固定**。`p=STAR` 単体でも `p=STAR フジテレビ ◯月◯日` のような日付入りでも投げ直さない（最初の1回の結果が放送カレンダーの正。休止週の判定もこれで済む＝「直近の放送回の特定」手順3）。
- **タイアップ追いフェッチは最大2曲まで**（資料① 手順4）。
- **billboard-japan.com トップ・fujitv.co.jp は直フェッチしない**（前者は情報なし、後者はドメインブロック）。
- **資料②の Grok は1サイクル1回だけ**（アーカイブパネルが直近放送回を未反映のときのみ）。反映済みならGrokもフォールバックのWebFetchも回さず、パネルを流用する。
- **資料②は B（TVer 2往復）→ A（Grok）の順**。TVer のセットリスト＋ナビゲーターを Grokプロンプトの事前情報にそのまま入れる（ドラフトからの吸い出しは TVer 不可時のみ）。
- **Grokは1プロンプト1往復・最初のポーリングは40秒後→以降20秒間隔（計2〜3回）・抽出は最後の「作業しました」以降を1〜2回で切り出し**（A 手順4）。
- **TVer は Chrome往復2回以内**（series 1 ＋ episode 1）。
- **WebSearch は 0回。**
