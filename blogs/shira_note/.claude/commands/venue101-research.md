Venue101（NHK総合の音楽番組）の記事をリライトする前に、資料①（次回放送の情報）と資料②（直前回の実際の出演順）を集める手順。**資料がユーザーから渡された回は、このファイルは読まない。**

完了条件：整形した資料①②を `tools/output/venue101_material.md` に保存し、チャットでユーザーの承認を得ること。承認前にリライト本編へ進まない。

（2026-09-25 実地テストで確定。Yahoo検索・ミラー記事の取得と、Grokの調査プロンプト［直前回9/12で検証］を実際に動かして確かめた。）

## いつ調べるか（発表のタイミング）

Yahooの記事の配信日時から見た、出演者の発表は**放送の1〜2日前（木曜〜金曜）**が中心（7/23木、7/31金、8/28金、9/4金、9/10木、9/24木）。さらに、放送当日の夕方にvoisが全体像の記事を出す回がある（8/29 19:36、9/5 18:03）。

| リライトする時期 | 主①で次回放送の記事が… | 判断 |
|---|---|---|
| 放送の3日以上前（月〜水曜の前半まで） | 0件 | **「出演者未発表」で確定。追加検索しない**（Googleも試さない）。プレースホルダー運用（エンジン0章） |

## 資料① リサーチ手順

1. **主① Yahoo検索をWebFetch（1回）。** プロンプトは「**『Venue101』（NHK総合の音楽番組）の放送回に言及する記事だけを、放送日ごとに列挙（見出し・配信元・配信日時・記事URL）。Venue101以外は除外。今日以降で最も近い次回放送を報じる最新記事を明示。曜日ラベルは信用せず日付の数値を正とする。本文要約は不要。記事URLは news.yahoo.co.jp/articles/... 形式で**」。クエリは `p=Venue101` 固定（言い回しを変えて投げ直さない）。
2. **主② 次回放送の記事を1〜2本WebFetch。** 優先は「全出演者＋歌唱曲が載る記事（THE FIRST TIMES／音楽ナタリー）」→「企画の全体像が載る記事（vois／TVガイドWeb）」。プロンプトは「**M月DD日放送のVenue101について抽出：放送日・放送開始/終了時刻・放送時間・チャンネル／WEEK構成（EXTRA等の特別編成名と、次週以降の予定）／MC／全出演アーティスト／各アーティストの歌唱曲（曲名をそのまま）／初披露・コラボ・特別企画／出演順・タイムテーブルの記載の有無／見逃し配信の記載。記事にない項目は『記載なし』。憶測で補わない**」。
3. **検索結果ページのサマリー（曜日・出演者）は信用しない。** 実例：2026-09-25の取得で、同じ検索結果が9/26を「金」と「土」の両方で返した（実際は土曜）。**放送日は記事本文の数値を正とし、曜日は本文の記載で確定する。**
4. 曲・出演者に欠落があるときだけ、別媒体のミラー記事をもう1本取ってクロスチェックする。
5. 特別編成（EXTRA・拡大版SP等）は、**番組名のラベル（例：「Venue101 EXTRA」）と、WEEK構成・次週の出演者**を必ず控える（タイトル・見出しに使う）。次週分は、記事に載っていれば資料①に「次回（次週）」として別枠で残す。
6. 放送時間は**記事の記載を正**とする。記事に終了時刻がなく、放送まで8日以内の回だけ、EPG（bangumi.org）で確認してよい（**8日より前は載らない**ので、それより先の回では試さない）。

> **資料①の完了条件**：放送日・放送時間・特別編成名（あれば）・全出演者が確定していること。歌唱曲は判明分がすべて拾えていること（未発表分は「未発表」と明示）。次週の情報があれば別枠で控えていること。揃わない項目は承認提示時に明示する。

## 直近の放送回の特定（資料②の前に必須）

「先週の土曜」を機械計算しない。**放送は毎週とは限らない**（実例：8/8・8/15・8/22は記事が無く休止、9/19も記事なし）。

1. 現在の `draft_venue101.txt` のメイン記事の放送日を第一候補とする（下書きが未作成の初回は、主①の放送カレンダーの「今日より前で最新の放送日」）。
2. 主①の「放送日ごとの記事一覧」で、候補より後・今日より前に別の放送日がないか確認する。**その週に記事が1本もなければ休止とみなす**（日付入りの追加検索はしない。承認提示で「確信度：中（記事の不在から判断）」と1行添える）。
3. 「実際の出演順【放送後更新】」パネルの日付と照合する：
   - パネル日 ＝ 直近放送回 → 資料②は取得済み。**Grokをスキップ**しパネルを流用。
   - パネル日 ＝ 直近放送回のちょうど1回前（休止週は挟んでよい）→ 正常。**Grokを実行**。
   - パネル日が2回以上前 → 直近放送回でGrokを実行。間の回は詳細データ欠落として承認提示時に明示。
4. 直近の放送回が一意に決まらないときは、Grokを回さず「直近は◯月◯日で合っていますか」とユーザーに確認する。

> **取り違え注意**：「実際の出演順」パネルの現在の中身は**前々回**のデータで、今回の資料②で上書きされる。資料②＝ここで特定した直近放送回。前々回データは過去一覧へ移す別物（エンジン手順1'・10）。

## 資料② リサーチ手順（Grokのみ）

資料②は**直前回の実際の出演順・時間帯・SNS反応**。**Grok（Xの実況分析）だけで組み立てる**（TVerは使えない）。

**実行するのは**「直近の放送回の特定」手順3で Grokを実行 と判定した場合のみ。

**事前情報の抽出（プロンプトへ差し込む）**：直近放送回の情報は**WebFetchで取り直さない**。優先順は ①`tools/output/venue101_material.md` の「前回の資料①」（企画・トーク・曲まで揃っている。下の「組み立てと承認ゲート」で毎回残す） ②上書き前の `draft_venue101.txt` の現メイン記事（出演者カード・JSON-LD `performer`）。①も②も無いとき（初回・保存し忘れ）だけ、資料①の記事をWebFetchする。

| プロンプトの `[ ]` | 供給元 |
|---|---|
| 放送日／放送時間 | 「前回の資料①」または現メイン記事のヘッダー |
| 出演アーティスト・既知の歌唱曲 | 「前回の資料①」または出演者カード群 |
| 主な企画・トーク | 「前回の資料①」（無ければ資料①の記事） |
| 特別編成名 | 資料①（通常回は「通常回」） |

### A. Grok（実行手順・最短4呼び出し）

**先に1回だけ**：ToolSearchで `select:WebFetch,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__javascript_tool,mcp__claude-in-chrome__tabs_close_mcp` をまとめて読み込む（`tabs_context_mcp` は不要）。

1. `navigate`（**tabIdを省略**、url=`https://grok.com`）→ タブが自動で開き、返り値に tabId が入る（ログイン済みChromeが前提）
2. `javascript_tool`（送信）：下の「送信スニペット」を1回
3. `javascript_tool`（完了確認＋取り出し）：下の「取り出しスニペット」を1回。`done:false` のときだけ同じものをもう一度
4. `tabs_close_mcp` でタブを閉じる

`screenshot` / `read_page` / `get_page_text` は常時通信のページでタイムアウトするので使わない（`env_grok_chrome_automation.md` 準拠）。

> **実測（2026-09-25・9/12回）**：この手順は呼び出し4回・読み取り約700字で終わり、出演順は従来型と同じ結果（MON7A→BOYNEXTDOOR→ハク。→中島健人）。従来型（長文プロンプト＋「作業しました」を目印に抽出）は約8回・読み取り約7,000字で、途中で切れて取り出しをやり直す手間があった。

**送信スニペット**（`P` に下のプロンプトを入れる。JS1回の待ち時間は約23秒＝CDPの約30秒上限内）：

```js
await new Promise(r=>setTimeout(r,2500));
const P=`（下のプロンプトを実値に置換して貼る）`;
const el=document.querySelector('.tiptap.ProseMirror'); el.focus();
const dt=new DataTransfer(); dt.setData('text/plain',P);
el.dispatchEvent(new ClipboardEvent('paste',{clipboardData:dt,bubbles:true,cancelable:true}));
await new Promise(r=>setTimeout(r,1000));
const b=document.querySelector('button[aria-label="送信"]'); if(b) b.click();
await new Promise(r=>setTimeout(r,20000));
({sent:!!b})
```

**取り出しスニペット**（完了＝末尾が「N sources」で、停止ボタンが無く、文字数が変わらない。答えは目印「【再現結果】」から取る）：

```js
const get=()=>{const b=[...document.querySelectorAll('.message-bubble.relative.rounded-3xl')];return b.length?b[b.length-1].innerText:''};
let prev=-1, stable=0, t='';
for(let i=0;i<9;i++){ t=get(); const done=/\d+ sources\s*$/.test(t)&&!document.querySelector('button[aria-label="停止"]'); if(done&&t.length===prev){stable++;} else stable=0; if(stable>=1) break; prev=t.length; await new Promise(r=>setTimeout(r,3000)); }
const i=t.lastIndexOf('【再現結果】'); const body=(i>=0?t.slice(i):t).replace(/[ \t]+/g,' ').replace(/\n{2,}/g,'\n');
({done:stable>=1, total:t.length, bodyLen:body.length, anchorFound:i>=0, head:body.slice(0,2800)})
```

- `anchorFound:false` のときは Grok が目印を付けなかった。`body`（全体）から「およその時間帯／時間帯」の表を探して読む。
- 返り値は約2,800字で切れる。`bodyLen` が2,800を超えたら、同じスニペットの最後の `head:` を `body.slice(2800)` に変えて続きを1回取る（通常は超えない）。
- 上限は約7分（通常回は完了まで約20〜50秒）。

**Grokプロンプト**（約750字。`[ ]` は実値に置換してから貼る。企画・トークが無い回は該当行を削除）：

```
あなたはメディア分析官です。[放送日、例: 2026年9月12日]放送のNHK総合「Venue101」[特別編成名があれば「Venue101 EXTRA」等]の登場順を、Xの実況投稿のみから時系列で再現してください。
事前情報（検索の手がかりにのみ使用）:
- 放送: [23:00〜23:30 等、資料①で確定した時間]／MC: 濱家隆一・生田絵梨花／構成: ライブとスタジオトーク・企画が交互
- 出演と曲: [アーティスト「曲名」を全組・全曲、わかっているものをすべて]
- 企画・トーク: [資料①の記事にあるトーク内容・企画名]
対象期間: [放送日] [開始の5分前]〜[終了の約30分後]の投稿のみ。
方法:
- x_keyword_search（Latest）とx_semantic_searchを複数回使い、since:[放送日 YYYY-MM-DD] until:[翌日 YYYY-MM-DD] を必ず指定。語は「Venue101」「#Venue101」に各アーティスト名・曲名を組み合わせる。
- 番組公式の「NOW ON AIR」投稿と、各アーティストの投稿急増の最初の時刻を基準に登場順を決め、5分単位で時間帯を推定（45分以上の回は5〜10分単位）。
- 全出演者・全曲を漏れなく配置。不明・投稿が少ない箇所は「順番推定困難」「推定」と明記。
出力（厳守・簡潔に）:
1行目は「【再現結果】」。次に全体傾向を2文以内。続けて表（列: 時間帯｜種別(ライブ/企画/トーク)｜内容(60字以内)｜反応(40字以内)）。最後に「登場順まとめ」を1行（A→B→C）と「最も投稿が伸びた瞬間」を1文。
禁止: X投稿以外の情報を結果に使うこと（検索語の精度向上にのみ可）。
```

> **実測での気づき**：Grokは番組公式の「NOW ON AIR」投稿（出演者ごとの登場時刻が分かる）を手がかりに出演順を再現する。公式アカウント名を指定しなくても、検索語「Venue101」だけで拾えた。**公式X・TVerでの裏取りはできないため、出演順の確信度は「中」**とし、投稿が少なかった組は「推定」と明記して残す。放送終了時刻が資料①に無い回（例：8/29）は、プロンプトの「放送」欄を「終了時刻は不明。投稿から判定して明記」に変える。

### C. 仕上げクロスチェック

- 出演順が、資料①の記事の並び（出演者名の発表順）と食い違っていても異常ではない（発表順は放送順とは限らない：9/12は記事が「中島健人・ハク。・BOYNEXTDOOR・MON7A」、実際の放送はMON7Aが先頭）。矛盾ではなく**発表順≠放送順**として扱い、Grokの時系列を採る。
- 時間帯は5分単位が限界。分刻みが取れない組は「○組目」の順序だけ確定する。

**フォールバック**（Chromeが使えない／Grokが応答しない）：パネルの内容を資料②として流用し、SNS反応・時間帯は空欄にする。

## 組み立てと承認ゲート

1. 収集結果を「資料② INPUT テンプレート」形式に整形し、資料①（放送日・放送時間・特別編成名・MC・出演者・歌唱曲・企画・次週の予定）を箇条書きでまとめる。資料②は「出演順・時間帯・SNS反応はGrokのX実況分析による推定（公式・TVerでの裏取りなし）」と明記する。
2. `tools/output/venue101_material.md` に保存する。**構成は「今回の資料①②」＋「前回の資料①」の2段**（保存前に、それまでの「今回の資料①」を「前回の資料①」へ移し、古い「前回」は捨てる）。前回の資料①は次回Grokの事前情報になる＝記事の取り直し（WebFetch）が不要になる。
3. **整形した資料①②をチャットに提示し、承認（または修正）を得てからリライト本編へ進む。** 憶測での補完・確信度が低い項目・「記載なし」の項目は明示する。
4. **承認依頼と同時に、今回のアイキャッチ画像URLも尋ねる。** 回答がなければ「据え置き」で本編へ進んでよい。

## 精度・トークンガードレール

- **資料①は「主① Yahoo検索1回 → 主② 記事1〜2本」が基本（合計2〜3フェッチ）。** クロスチェックが要るときだけミラー記事を1本足す。
- **Google Newsは、判定表の条件（放送3日前以降・主①で0件）のときだけ、Chromeで1回**。常用しない。
