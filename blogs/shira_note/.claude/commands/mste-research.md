# Mステ リライト用 資料①②リサーチ

`/mste-rewrite` で資料①（または資料①②とも）が渡されなかった回に、本編リライトへ入る前に実行するリサーチ手順。

**このファイルを読むのは「資料が渡されなかった回」だけ。** 資料が渡された回は `mste-rewrite.md` の手順1へ直行する（このファイルは読まない）。

完了条件：整形した資料①②を `tools/output/mste_material.md` に保存し、チャットでユーザー承認を得ること。承認前に `mste-rewrite.md` 手順1へ進まない。

## 使用ソースと取得順（トークン節約のため最小構成）

| 優先 | ソース | 取得方法 | 役割 |
|---|---|---|---|
| 主 | Yahoo!ニュース検索 `https://news.yahoo.co.jp/search?p=ミュージックステーション&ei=utf-8` | WebFetch 1回 | 次回放送を報じる最新記事のURL特定 |
| 主 | 上で特定した記事（通常は音楽ナタリー or MANTANWEB のYahooミラー） | WebFetch 1回 | 放送日時・全出演者・全歌唱曲・初披露/コラボ/特別編成の確定 |
| 副 | Yahoo検索結果の別媒体記事（ORICON等） | WebFetch 1回 | 曲名欠落・出演者不足時のクロスチェックのみ |
| 補助 | `tools/output/programs.md`（collect_news.py の出力） | Readのみ（fetchなし） | 放送枠の確定 |
| 三次 | dメニュートピックス `https://topics.smt.docomo.ne.jp/latestnews/keywords/b19025b930322e49c97df571f73cae1a668f8ddc839c46d392b674def57698da` | WebFetch 1回 | Yahoo検索が取得不可のときだけ |
| 任意 | テレ朝Mステ公式 `https://www.tv-asahi.co.jp/music/` | Claude in Chrome | 上記すべてで裏が取れないときだけ（WebFetch はドメインブロックで不可） |

> **WebSearch は使わない。** natalie.mu / tv-asahi.co.jp への直リンク WebFetch はブロック（403 / ドメインブロック）されるため使わず、記事は必ず Yahoo ミラー（`news.yahoo.co.jp/articles/...`）経由で読む。

## 資料① リサーチ手順

1. Yahoo!ニュース検索を WebFetch。プロンプトは「**『◯月◯日放送のミュージックステーション』に言及する記事を、過去分・今後分まとめて放送日ごとに列挙（見出し・配信元・配信日時・記事URL）。うち次回放送（＝今日以降で最も近い放送日）を報じる最新記事1〜2本を明示**。本文要約は不要」と絞る（返り値を小さく＝トークン節約）。この一覧が「実際の放送カレンダー」になり、飛んだ週・特番週の判定と『直近の放送回の特定』（下記）に使う。
2. **Yahoo検索結果ページのサマリーに並ぶ出演者・曲名は信用しない**（別日のゲストや密着記事の名前が混ざる。9/4分では実在しない Hearts2Hearts / NCT WISH が出た）。手順1の一覧は「どの記事を読むか」の特定だけに使い、出演者・曲は必ず**専用記事（音楽ナタリー／MANTANWEB の本文）を WebFetch して確定**する。抽出項目：放送日・放送時間・チャンネル／全出演アーティスト／**各歌唱曲（曲名を省略・要約せず全曲そのまま）**／初披露・コラボ・特別企画・VTR企画／特別編成名（○○回SP等）／記事が出演順・セットリストを報じていればそれも。**記事にない項目は「記載なし」とし、憶測で補わない。**
3. 歌唱曲が欠落、または出演者が明らかに一部のみのときだけ、Yahoo検索結果の別媒体記事を1本だけ追加で WebFetch。
4. **曲のタイアップ・背景注記**（例：「福山雅治『邂逅』は映画◯◯主題歌」）が記事にない曲は、**明らかな定番曲を除き最大2曲まで**、その曲を報じる記事を1本ずつ追いフェッチする。3曲以上不明なら追わず、該当カードは「◯◯を披露。」の最小記述にする（＝9/4の絢香・平井大と同粒度。違和感なし）。
5. 放送枠（開始・終了時刻）を確定する。**「通常回は20:00〜」と思い込まない**（枠は毎回変動する。例：2026-09-18回は21:00〜）。取得順は「`tools/output/programs.md` を Read → 無ければ記事記載の開始時刻＋通常54分枠（`21:00〜21:54` 等）を仮置きし、承認提示時に**終了時刻＝要再確認**と明示」。**bangumi.org EPG は放送の約8日前からしか載らない**ので、それより先のリライトでは EPG を試さない（404になるだけ）。**特別編成が判明している回だけ**、放送8日前以降に EPG（bangumi.org）で開始〜終了を確定する。確定した「HH:MM〜HH:MM」は FAQ Q1・aside・JSON-LD で共通利用する。
6. Yahoo検索が取得不可の場合のみ dメニュートピックスを WebFetch。それも不可なら公式サイトを Claude in Chrome で確認。どうしても出演者が確認できなければ「出演者未発表」として扱い、`mste-rewrite.md` の「資料①が『出演者未発表』の場合」のプレースホルダー運用に切り替える。

> **資料①の完了条件**：全出演者・全歌唱曲が確定していること。加えて、記事に出演順・タイムテーブルの記載があればそれも正確に転記していること（分刻みタイムテーブルは事前公開されないのが通常。無ければ出演順は「未発表・放送後更新」とする）。この3点が揃わない項目は承認提示時に赤字相当で明示する。

## 直近の放送回の特定（資料②の前に必須）

「先週の金曜」を機械計算しない（Mステは毎週放送とは限らず、飛ぶ週・特番週がある）。次の手順で確定する。

1. `draft_mste.txt` の**現在のメイン記事の放送日**を読む（＝前回リライトが用意した回）。これを直近放送回の第一候補とする。
2. その日付が **今日より前**なら、放送済み＝直近放送回の候補として確定に進む。今日以降（未放送）なら、直近放送回はアーカイブパネル（`mste-rewrite.md` 手順8）の日付。
3. 資料① 手順1で得た「放送日ごとの記事一覧」を照合し、**候補より後・今日より前に別のMステ放送日がないか**確認する。あれば最も新しいその日を直近放送回に更新する。
4. **アーカイブパネル（`mste-rewrite.md` 手順8）の日付と照合**：
   - パネル日 ＝ 直近放送回 → 資料②は取得済み。**Grokをスキップ**しパネルを流用。
   - パネル日 ＝ 直近放送回のちょうど1回前 → 正常。**Grokを実行**（下記）。
   - パネル日が2回以上前（サイクルスキップ）→ 直近放送回でGrok実行。間の回は granular データ欠落として承認提示時に明示。
5. 上記で直近放送回が一意に確定できない場合は、**Grokを回さず「直近の放送回は◯月◯日で合っていますか」とユーザーに確認**してから進む。

ここで確定した日付・（特番なら）特別編成名を、下のGrokプロンプトに実際に埋め込む。

## 資料② リサーチ手順（Claude in Chrome ＋ Grok）

資料②は**直前回（＝上で特定した直近放送回）の実出演順・時間帯・SNS反応**。一次情報源はXなので、Xにアクセスできる Grok で取得する。

**実行するのは**「直近の放送回の特定」手順4で **Grokを実行** と判定した場合のみ。スキップ判定ならこの節を飛ばし、パネル内容を資料②として使う。

**事前情報の抽出（プロンプトへ差し込む。ドラフト上書き前に実施）**
「直近の放送回の特定」で確定した回のデータは、**上書き前の `draft_mste.txt` の現メイン記事**から吸い出す。

| プロンプトの欄 | 供給元（draft_mste.txt 内） |
|---|---|
| 放送時間 | 現メイン記事ヘッダーの放送枠（例 `2026年9月4日(金) 21:00〜21:54`） |
| 出演アーティスト＆歌唱曲 | 手順5 ARTIST LINEUP カード群（＝全組・全曲。JSON-LD `performer` でも可） |
| 主な企画・特徴／既知の歌唱曲 | 見どころ・VTR企画の記述・「初披露」等のバッジ |
| 分析対象期間・since/until | 上記の放送日・放送枠から生成（放送開始〜終了＋約1時間） |

**取得手順**（`env_grok_chrome_automation.md` の回避策に準拠）
1. `mcp__claude-in-chrome__tabs_context_mcp` で状態確認 → 新規タブ → `grok.com` へ navigate（ログイン済みChromeが前提。未ログイン・拡張不可なら下の「フォールバック」へ）。
2. ページ確認・要素操作は **`javascript_tool` のみ**（`screenshot`/`read_page`/`get_page_text` は常時通信SPAでタイムアウトするため使わない）。
3. 入力欄 `.tiptap.ProseMirror`（contenteditable）へ **`DataTransfer` ＋ `ClipboardEvent('paste')` を合成**してプロンプトを一括投入（`computer.type` は改行で誤送信される）。送信は `button[aria-label="送信"]` をクリック（投入直後に出現）。
4. **完了検知**：`.message-bubble.relative.rounded-3xl` 最終要素の `innerText` を ~20秒間隔でポーリングし、**テキスト長が2回連続で不変** かつ 末尾に「`Ns 作業しました`／`作業内容: Ns`」が出ていれば完了。`button[aria-label="停止"]` は Grok 側のラベル差でヒットしないことがあるため判定に使わない。**上限7分**（通常回 約2分、SP 4〜6分）。完了したら **1回だけ** 全文を抽出（検索ログ部分は捨て、答え本文＝ヘッダー＋時系列表＋補足のみ採用）。
5. Grokプロンプト（1回・改行あり）。**`{ }` は事前情報の抽出で得た実値に置換してから投入**（プレースホルダーのまま送らない）。通常回なら番組名の `{／特別編成名}` は削除：
   ```
   あなたは高度なメディア分析官です。{放送年}年{M}月{D}日（{曜}）放送の「ミュージックステーション」（Mステ）{／特別編成名}の番組構成を、Xの実況投稿のみからできる限り詳細に、かつアーティスト個別の登場順を厳密に追いかけて時系列再現してください。

   【事前把握情報（検索精度向上のためのガイドのみ使用）】
   ・放送時間: {HH:MM}～{HH:MM}
   ・出演アーティスト＆歌唱曲:
   {- アーティスト名「曲名」（初披露/コラボ等の注記） …全組}
   ・主な企画・特徴: {VTR企画・コラボ・初披露・MC/サブMC等}
   ・既知の歌唱曲: 上記の通り

   【分析対象期間】{放送日} {HH:MM}～{終了+約1時間}頃 までの投稿に厳密に限定。

   【使用ツール方針（必須・最重要）】
   ・x_keyword_search（Latestモード）と x_semantic_search を複数回・段階的に・重層的に使用
   ・時間指定 since:{YYYY-MM-DD} until:{翌日YYYY-MM-DD} を必ず使用
   ・アーティスト個別順番追跡を最優先とし、次の手順で徹底調査：1.オープニング・序盤ライブを1組ずつ 2.各ライブ・トークセクション 3.中盤・後半のメインライブ・企画 4.エンディング付近
   ・各アーティストごとに複数パターン検索：「[名] Mステ」「[名] 歌ってる」「[名] 披露」「[曲名] Mステ」「[名] トーク」「今 [名]」「[名] 始まった」「[名] 終わった」
   ・投稿急増の最初期タイムスタンプと投稿密度のクラスターから5〜15分単位で開始時間を詳細に推定

   【分析の重要方針（最優先）】
   ・事前情報の全アーティストと全歌唱曲を漏れなく配置し、登場順をできる限り厳密に再現
   ・スタジオライブの歌唱力・演出・カメラワーク、アーティスト同士のトーク、コラボ・初披露の反応を重視
   ・順番が不明瞭・投稿が少ないアーティストは「順番推定困難」「言及少なめ」と正直に明記
   ・ライブ→トーク→次ライブの流れも特定

   【出力形式（厳守）】
   最初に簡単なヘッダー（放送日・全体傾向・推定放送時間）を付けた後、以下のMarkdown表で出力。
   | およその時間帯（投稿タイムスタンプに基づく） | コンテンツ種別（オープニング/ライブ/トーク/企画/エンディング） | 詳細内容 | 視聴者の反応・盛り上がりの特徴 |
   | :--- | :--- | :--- | :--- |

   【特に記載してほしい点】最も投稿爆発した瞬間とその時間帯／アーティスト個別の登場順の全体まとめ（表の後ろに補足）／ライブとトークの連動・切り替わり／Mステらしい高品質ライブ・演出への評価

   【禁止事項】Xの実況投稿とそのタイムスタンプのみをソースにする／一般知識・公式情報・事前記事は一切使用禁止／事前情報は検索キーワードの精度向上にのみ使用
   ```
6. 回答を CLAUDE.md「資料② INPUT テンプレート」へマッピング：

   | Grok出力 | 資料②テンプレの行き先 |
   |---|---|
   | 時系列表の各行（時間帯・種別・詳細） | セットリスト表：時間帯／アーティスト／歌唱曲／備考（初披露・コラボ等） |
   | 表の後の「登場順まとめ（推定）」 | セットリスト表の並び順を確定（○組目） |
   | 「最も投稿が爆発した瞬間」 | Key_Insight（なぜ伸びたか）＋ Top_Tweet（傾向の要約・引用不要） |
   | ヘッダーの「推定放送時間」「全体傾向」 | REPORTコメント欄／前々回パネルの放送枠更新の参考 |

   **Grok出力は X実況からの推定なので確信度を付す。「順番推定困難」と明記された組はその旨を残す。Impression は使わない。**
7. 出演順は draft_mste.txt のアーカイブパネル（前々回）や資料①記事の発表順と矛盾しないか1点だけクロスチェックし、矛盾があれば承認提示時に明示。
8. 時間帯が5〜15分単位でしか取れないのは正常（Grokの仕様どおり）。分刻みが無い組は「○組目」の順序だけ確定する。

**フォールバック**（Chrome拡張が使えない／Grokが応答しない）
アーカイブパネルの内容を資料②として流用し、Yahoo!ニュース検索 or Togetter で直近回のセットリスト記事を1本だけ WebFetch して出演順・歌唱曲の食い違いだけ検証する。SNS反応・時間帯は空欄のままにする。

## 組み立てと承認ゲート

1. 収集結果を CLAUDE.md の「資料② INPUT テンプレート」形式に整形し、あわせて資料①（放送日・放送枠・出演者・歌唱曲・見どころ・特別編成）を箇条書きでまとめる。
2. 整形結果を `tools/output/mste_material.md` に保存する（レビュー・修正用の記録）。
3. **整形した資料①②をチャットに提示し、ユーザーの承認（または修正）を得てから `mste-rewrite.md` 手順1以降に着手する。** 憶測での補完箇所・確信度が低い項目・「記載なし」の項目は明示する（CLAUDE.md ガードレール準拠）。

## 精度・トークンガードレール

- **Yahoo検索フェッチは「放送日ごとに 見出し・配信元・配信日時・記事URL だけ。本文要約は不要」で固定**（緩いプロンプトだと数十記事の本文ダンプが返りトークンを浪費する）。
- **タイアップ追いフェッチは最大2曲まで**（資料① 手順4）。
- **資料②の Grok は1サイクル1回だけ**（アーカイブパネルが直近放送回を未反映のときのみ）。反映済みなら Grok もフォールバックのWebFetchも回さず、パネルを流用する。
- **Grokは1プロンプト1往復で完結させる**。追い質問はしない（順番推定困難な組はその旨を残す）。
- **Grokの生成待ちは ~20秒間隔のポーリング**（テキスト長チェックのみの軽いJS）。完了後に **1回だけ** 全文抽出。ポーリングを短間隔で何度も回さない。上限7分。
- **WebSearch は 0回。** 公式・natalie 直リンクの WebFetch も試さない。

| ケース | ツール呼び出しの目安 |
|---|---|
| 通常（資料①：WebFetch 2〜4回／資料②：Grok DeepSearch 1回＝約2分・ポーリング数回＋抽出1回） | WebFetch 2〜4回 ＋ Chrome 数往復 |
| 資料②がパネル反映済み（Grok不要） | WebFetch 2〜4回のみ |
| 主ソース失敗でフォールバック | WebFetch +1〜2回 |
