# UYA. 記事生成システム

`/uya-theme`の引き継ぎ情報を受けて、構成設計・本文生成・品質チェック・保存まで行うシステム。
引き継ぎ情報がない場合は「テーマ・種別・タイトルを教えてください」と確認してから開始する。

**構成案の提示と合意を飛ばして本文を書き始めない**（ルート`CLAUDE.md`の共通ルール）。Step 1で必ず立ち止まる。

**テーマ・読者像・キーワード・タイトルのどれかが未確認なら、構成に入らず `/uya-theme` の該当ステップへ戻る。タイトルの基準は `/uya-theme` Step 3 が正。**

---

## 開始時に読むファイル（むだに読まない）

2. `uya/shared/personal_data.md`（必須）← 事実・数字・開示ルール。**ここにない体験・数字は使わない**
3. `uya/examples_essay.md` の1〜3・5〜7・10節（必須。Step 2の前）← 文体・見た目。9節は投稿用なので読まない

6. `docs/reference/note_paid_article_writing_reference.md` ← **有料記事のときだけ**
7. `uya/rules/hashtag_candidates.md` ← Step 4のときだけ

## Step 1：構成設計

### H2設計ルール

**基本の流れ（当事者記録エッセイ）**：
場面・きっかけ → 何が起きたか（事実） → その時どう感じたか → 今はどう考えているか（変化）

**冒頭はH2なしで本文から直接始める**（「この記事では〜について解説します」で始めない）。**得（数字・結果）を先に出し、続きを読む理由（裏側・過程）を1つ見せる。**体験の語りが中心の記事は、つぶやきのように入ってよい。

**実用寄りの記録型（AIの使い方・仕事のやり方の記録）のとき**は、上の流れより、結果を先に言い切り→やり方→うまくいかなかったこと→まだ残っていること、の順を優先する。経緯は導入で短く触れる。

- **構成案の前に、材料を質問で集める**（「前は何分かかったか」「何がうまくいかなかったか」「いまも手でやっているのは何か」等）。`shared/personal_data.md`にない事実は、質問して確かめてから書く
- 各H2に「何のシーンを・どこまで具体的に書くか」の執筆方針と、前のH2から何でつなぐか（理由／対比／言い直し）を付ける
- H2は3〜5本に絞る
- H2に、`/uya-theme` で採用した見出し用キーワードを自然に入れる。得になる中身か具体的な場面・数字を入れる。好奇心だけで中身のない見出しにしない。見出しが、実際の中身と食い違わないか確かめる
- 全H2のうち最低1本に、読者の状況（会社に行くのがつらい・人前が苦手・収入の波 等）に触れるキーワードを含める
- H2だけを縦に読んで記事の流れが追えるか、設計後に確認する

### H3の使用判断

原則H3不要。1つのH2内に複数の独立した段階・情報があり、H3なしでは読者が迷子になる場合のみ使う。**構成案には、H3を使うか使わないかを、理由つきで1行書く**（例：「H3なし。各H2が約600字で、箇条書きで足りるため」）。見直す条件（H2が900字超・全体が3,500字超など）も添える。

## Step 2：本文生成

### 語り口のルール

- **一人称**：「私」（文の流れによって「自分」も使ってよい）
- **押しつけない、静かな語り口＋カジュアルな口調**。s4lvの「謙虚な実力者」的な抑えたトーンとは違う、素の言葉・砕けた言い回し（`rules/project_uya_positioning.md`参照）
- **口調の細部は `uya/examples_essay.md` 10節が正**（です・ます調を基調に、くだけた言い回しを混ぜる／2〜3文の段落／本人が言っていない理由を足さない／結びを教訓にしない 等）。最初の案の時点で守る
- **捏造禁止**：`shared/personal_data.md`にある事実の範囲内のみ。不明な部分はユーザーに確認してから書く
- **感情軸は正直な体験談そのもので作る**。作り物の危機感・煽りは使わない（PASONA的な表現辞典は不採用。2026-09-27決定）

### Sonnet系モデルで書くときの補強（2026-10-01・UYA.の1テーマで検証。仮説を含む）

**Sonnet 5.5（medium／high）で本文を書くときは、`docs/reference/note_writing_model_tips.md`の「2. 補強の指示」（A〜E）を本文生成の依頼に加える**。要点：①各H2の要点とつなぎ方を先に決めてから書く ②材料の範囲で具体に言い換え、新しい出来事・気持ちは足さない ③結びは `examples_essay.md` 10節6に従う（体験の結果で終える。教訓・呼びかけにしない） ④文末「〜て。」を3割以内に ⑤保存前に字数を数える。初稿に声の薄さ・つなぎの弱さを感じたら、同じ指示をhighで1回だけ書き直す。手直しの1回（同ファイル3章）はまだ試していない仮説。

### 機械的ルール（`brands/writing/writing_core.md`より。トーンに関係ない部分のみ）

- 疑問文には「？」。読点は意味の切れ目だけで目安2つまで。1文は目安70字まで（`qa_article.py`が検知する）
- 「作る側の用語」（ペルソナ・フック・ベネフィット等）を本文に出さない
- CTAを入れるときは具体的に。ただし無料の記録型の記事は、呼びかけで終えない（`examples_essay.md` 10節6）
- 使わない：PASONAの五感描写・危機感の煽り、「体験談に見えないようにする」書き方（2026-09-27決定。UYA.は当事者記録が差別化ポイント）

### 見た目（改行・引用・太字）

`uya/examples_essay.md` の5〜7節が唯一の正。ここには写さない。太字・引用を入れたら、**必ずnoteのプレビューで実際の表示を確認する**。

### 扱ってはいけない話題（`shared/personal_data.md`「開示ルール」参照）

- 本名・顔、年齢
- 過去の職種名（「体を使う仕事」等に留める）・けがの病名（「首の持病」等に留める）
- パチスロの立ち回り・勝ち方・設定判別・店名・機種の推し・使った金額／勝ち額
- 運営しているブログ・note名（ジャンル程度は可）

### 収益の数字を使うとき

- s4lvと同じ具体的な数字（1日170万円、確定約160万円 等）を使ってよい（2026-09-27オーナー確認）
- ただし**購入を煽る使い方はしない**。有料記事の販売文に置かない。報酬画面のスクリーンショットは使わない。低い月もセットで書く

## 有料記事モード（種別に「有料記事」が指定された場合のみ適用）

- 無料パートは、この記事単体で判断材料が揃うようにする（目安800〜1,500字）。有料ラインは1本のみ。誘導文は2〜3行・煽らない（`docs/reference/note_paid_article_writing_reference.md`参照。価格は `note_monetization_reference.md` の相場。字数で稼がない）
- UYA.固有の判断（2026-09-27決定）：①「参考書型」「体験談を隠す」書き方はしない ②タイトルは変化が静かに見えるものにする ③継続更新前提の記事は、冒頭のアップデート情報を大きな更新だけに絞りスマホ1画面に収める ④感情の部分は正直な体験談が担い、「自分にもできるかも」と思える具体的な場面を入れる

## Step 3：品質チェック

本文生成後にチェックして直してから保存する。機械が見る項目（読点・文の長さ・文末の連続）は人の目では見ない。

**【事実と開示】**
- [ ] `personal_data.md`にない体験・数字・理由を足していないか。因果（〜のおかげ）を断定していないか
- [ ] 開示NG（職種名・病名・パチスロの金額・本名・ブログ名等）に触れていないか。収益の数字が購入を煽る書き方になっていないか

**【トーン・口調】**（`examples_essay.md` 10節）
- [ ] 当事者の記録になっているか（体系立てて教える書き方・煽り表現がないか）。冒頭は得を先に出しているか
- [ ] です・ます調が基調か。結びが教訓・呼びかけ・抽象語でなく、体験の結果か
- [ ] 見出しが中身と食い違っていないか。H2だけ縦に読んで流れが8割わかるか
- [ ] ジャンル名・ツール名を言い換えていないか（機能名には短い説明を添えたか）
- [ ] （Sonnet系のとき）文末「〜て。」「〜で。」が3割以内か／本文文字数が指示に入っているか

**【有料のみ】** 有料記事モードの判断と、`/uya-theme` Step 3の有料基準に合っているか

**【機械チェック（必須）】**

```
python brands/tools/qa_article.py "uya/articles/drafts/<ファイル名>.md"
grep -c "じゃん\|わけじゃなくて\|思います\|感じています" "uya/articles/drafts/<ファイル名>.md"
grep -c "よね" "uya/articles/drafts/<ファイル名>.md"
```

1行目（qa）は **ERROR 0件**（有料は `--paid`）。2行目（禁止の言い回し）は0件、3行目（「よね」）は2回以内であること。

**【初見のレビュー（公開前に1回だけ）】**
`note-ai-reviewer` と `note-beginner-reader` を並行で回す。再審査は、構成や結論を大きく変えたときだけ。指摘は、事実の整合・誤字・繰り返し・読者が迷う所に分けてオーナーに見せ、直す前に確認する。オーナーが自分で直した行は、勝手に戻さない。依頼文の雛形：

```
[ai-reviewer] パス：<下書き> ／ UYA.（無料）。文体の正は examples_essay.md 3・10節、事実の正は personal_data.md。オーナーが自分で直した口調は、AIっぽい定型でなければ指摘しない。禁止の言い回しは3節。画像の差し込み位置の目印は指摘不要。s4lvの有料案内の基準は対象外。見る点：①AIっぽい言い回し・言い直しの繰り返し ②当事者の声として不自然な所 ③事実の足し・誇張・断定 ④読者の気持ちの決めつけ ⑤語尾の偏り ⑥冒頭が続きを読ませる形か。qa_article.pyを実行し、行番号つきの表で返す。本文は書き換えない。
[beginner-reader] パス：<下書き> ／ 想定読者：<Step 1の読者像>。迷った所・数字を見失った所・話が飛んだ所・専門用語で止まった所を行番号つきで報告し、5段階の採点と「試そうと思えたか」を答える。本文は書き換えない。
```

## Step 4：ドラフト保存（本文出力と同ターンで実行・後回し禁止）

**保存先**：`uya/articles/drafts/`
**ファイル名**：記事テーマを簡潔に表した日本語

**ファイル先頭の管理情報**：

```
作成日：YYYY-MM-DD
種別：無料記事 / 有料記事（価格）
タイトル：
ハッシュタグ：
```

### ハッシュタグ選定（保存前に実施）

公式ルール・実在確認・お題の調べ方は `docs/reference/note_hashtag_reference.md` が正。短い取り方は `docs/reference/note_research_snippets.md`。

1. `hashtag_candidates.md` の一般タグから、**本文の中身と一致するものだけ**拾う（内容と無関係なタグは、付けても表示機会が増えない）。バンクにない候補は、実在確認と同ファイルの「採用基準」に照らす
2. お題・コンテスト：同ファイルの「最終確認日」が14日以内なら再確認を省き、お題表から合うものを探す。過ぎていたら `note_hashtag_reference.md` §4 の手順で確認して日付を更新する。賞目当てで、内容が合わない記事には付けない
3. 基本5個（外せないお題・ツール名タグがあるときだけ最大7個）。30字以内・ハイフン不可。パチンコ・パチスロを連想させるタグは使わない
4. 候補を提示し、**オーナーに選んでもらってから**確定する。新しいタグは `hashtag_candidates.md` に追記する

件数は実在確認のためのもので、需要の指標ではない。

## 注意事項

- テーマ・タイトルの見直しが必要な場合は `/uya-theme` を呼び出す
- 戦略的判断（立ち位置・価格・開示範囲の変更等）が必要な場合は `/notekaigi` を呼び出す
- 公開後は `uya/articles/published/` へ移動し `uya/articles/article_index.md` に登録する（ルート`CLAUDE.md`共通ルール）。手順：①下書きを `published/` へ**コピー**し、先頭に公開日を足す。画像の差し込み位置の目印は、説明の文に置き換える ②差分が意図した行だけか確認する ③公開ページのURLをオーナーに聞き、一覧に登録する ④本文と一覧の登録を確認してから、`drafts/` のファイルを消す（Git未追跡のファイルは、消すと復元できない）
- 記事を重ねるたびに、`uya/examples_essay.md`に新しいクセ・判断を追記していく（1本目の実地確認で新設済み）
