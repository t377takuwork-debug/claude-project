# Note記事生成システム

Note有料・無料記事をテーマ入力から完成まで一貫して生成するシステム。
会議は行わない。確定済みの原則を直接適用し、ユーザーの承認ポイントのみで進む。

## 呼び出し方

```
/note-article [アカウント名] [テーマ/ネタ]
```

例：
- `/note-article mbticode 繰り返す恋愛パターン`
- `/note-article s4lv Claude Codeで記事設計を効率化する`

**このファイルは「共通の進め方」だけ**（2026-09-21に、アカウント別の内容を専用ファイルへ分けて、s4lvの記事生成で読む量を、実測で約34%減らした）。アカウント別は次の専用ファイルが正：

| アカウント | 専用ファイル（最初に読む） |
|---|---|
| **s4lv** | `brands/s4lv/rules/note_article_checklist.md`（オーナーの意図の唯一の正。**資料をもらったら、最初の返信の前に0章を1回で確認**して、食い違いをまとめて質問する。公開後の8章まで） |
| **mbticode** | `brands/mbticode/rules/note_article_mbticode.md`（専用の読込・ペルソナ3軸・品質基準・視覚フォーマット・公開前チェックリスト・公開後の処理） |
| vivant／junk_juice | それぞれ `/vivant-article`／`/junk-article` を使う（このスキルの対象外） |

## 実行前の準備（読むのは、その段階で必要なものだけ）

`brands/writing/` の共通ルールは、**全部を最初に読まない**。段階ごとに、必要なものだけ読む。

| 段階 | 読むもの |
|---|---|
| Step 1 ペルソナ | アカウント別の専用ファイルだけ |
| Step 2 タイトル | `writing_headlines.md`（ケープルズ5基本ルール・35型）・`docs/rubrics/title_scoring.md`（採点表・採点してから提示。点数の捏造は禁止） |
| Step 3 構成 | `writing_note_structure.md`（3視点構造・H2設計・導入3要素） |
| Step 4 本文 | `writing_tone.md`（文体・トーン。共通核＋アカウント別上書き）・`writing_core.md`（PASONA・5大ルール・句読点・AI臭さ除去）。`writing_expressions.md`（表現パターン辞典）は、表現に詰まったときだけ |

**s4lv で追加で読むもの**（`note_article_checklist.md` に加えて）
- `s4lv/rules/project_s4lv_accounts.md` — 統一アカウント定義・アイデンティティ原則
- `s4lv/shared/personal_data.md` — 開示ルール表と実績（捏造禁止の根拠）
- `s4lv/articles/note_article_index.md` — 公開済み記事（過去記事との重なり確認）
- `s4lv/rules/s4lv_learnings.md` の「オーナーの好み → 共通」だけ（Grepで `^\*\*共通\*\*` から `^\*\*Note記事だけ\*\*` の前まで。全文は読まない）
- `s4lv/rules/project_s4lv_note_article_process.md` は、Note貼り付けの記法・現場の記録の型・有料の価格帯が要るときだけ

## Step 1：ペルソナ設計

「たった一人」の人物を描く。書き手の羅針盤として使う（タイトルには出さない）。

**mbticode**：専用ファイルの「Step 1」に従う（デモグラフィックを定義しない・心理3軸）。

**出力する項目（mbticode以外）**
- 年齢・属性・職業・状況
- この人が夜な夜な実際に検索する言葉（3〜5個）
- 今感じている感情（自己嫌悪・不安・怒り・疑問など具体的に）
- 求めている変化
- この人がお金を払う瞬間
- **この記事がこの悩みをどう解決するか（1行要約・必須）**

**ユーザー承認ポイント①**
「このペルソナ＋解決の方向性で進めますか？」と確認する。**承認なしにタイトル・構成へ進まない。**

---

## Step 2：タイトル生成

確定したペルソナを起点に、タイトル案を3つ生成する。

**ルール（変更不可）**
- 感情・行動・状況で書く（mbticodeはタイプ名・フレームワーク名をタイトルに入れない）
- Note編集部の3条件：具体性・読者メリットの明確さ・差別化
- ケープルズの4特徴：得になる・新情報・好奇心・手っ取り早さ
- サブタイトルは任意。付ける場合は「手に入るもの」を明示する
- Noteタイトル欄は45字以内を目安にする（s4lvは、`project_s4lv_note_article_process.md`「タイトル」の32字目安・40字上限に従う）

**チェックリスト（3案すべてに適用）**
- [ ] 読者の「得になる」要素があるか
- [ ] 暗い・否定的なイメージを植え付けていないか
- [ ] 一目で意味がわかるか
- [ ] 競合にない差別化された切り口か
- [ ] 読者の悩みそのもの（ペルソナが思っている言葉）か、続きが気になる引っかかりがあるか（説明調・安全な案だけにしない）

**出力フォーマット**
```
案A：[タイトル]
案B：[タイトル]
案C：[タイトル]

| 条件 | 案A | 案B | 案C |
|---|---|---|---|
| 読者の得 | | | |
| 手に入るものの明確さ | | | |
| 差別化 | | | |
| 感情フック | | | |
```
（体験談・現場の記録など、配点表が合わない記事は、その旨を書いて、配点表の採点を省いてよい）

**ユーザー承認ポイント②**
「どの案を選びますか？または修正指示をください」と確認する。

---

## Step 2.5：SEOキーワード確認（毎回必須）

タイトル案の承認前に、ペルソナが実際に検索する語句をWebSearchで確認する。

**目的**
Note記事はSNS流入だけでなく検索流入も重要な経路となる。ペルソナが検索する言葉をタイトルに組み込むことで、SEOと引っかかりを同時に狙う。

**実行手順**
① Step 1で特定した「夜な夜な検索する言葉」を3〜5語句、WebSearchで実在性を確認する
② 検索結果から、次を判断する：実在するキーワードか（競合記事が存在するか）／競合の切り口はどんな軸か（解説系・体験談系など）／自分の記事の差別化余地
③ 採用するキーワードを決定し、Step 2のタイトル案に反映して最終3案を出力する

mbticodeの採用基準（感情語句・娯楽系除外・トレンドワード表）は、専用ファイルの「Step 2.5」に従う。

---

## Step 3：見出し構成設計

**3視点の役割分担**

| セクション | 担当視点 | 内容 |
|---|---|---|
| 導入部 | 認知ハック・人間心理 | ターゲットの最大の痛み＋ベネフィット＋フック（s4lvは、`note_article_checklist.md` 2章が優先＝直球のベネフィット文を使わず、驚く発見を先に見せる） |
| 本論 | 論理的逆算・職人品質 | H2：3〜6本、各H2に執筆方針を付ける |
| 結論 | コミュニティ・物語設計 | 1つのアクション＋あえての隙 |

**H2の設計ルール**
- 読了率を最大化する本数に絞る（一律固定しない）
- 各H2に「何を・どこまで具体的に書くか」の執筆方針を必ず付ける
- ニッチ義務化：検索結果の要約記事禁止
- **H2タイトルにStep 2.5で確認した検索キーワードを自然に組み込む**

**H3の設計ルール**
- 各H2について「H3が必要かどうか」を必ず検討する。H3を使う基準：H2の内容が複数の独立したサブトピックに分かれる場合・段階・パターンを列挙する場合
- H3は1つのH2に2〜3本が上限（多すぎると読了率が下がる）。**1本だけは禁止**（機械QAが検知）
- H3タイトルにも可能な範囲でキーワードを組み込む

**出力フォーマット**
```
## 記事の前提（1行）
- 何が分かった記事ではなく、何に気づいた記事か：

## 導入部
- ターゲットの痛み：
- 先に見せる驚く発見／ベネフィット：
- フック：

## 本論
H2①：[見出しタイトル（キーワード含む）]
　執筆方針：
　H3：[サブ見出し]（不要な場合は省略）
　H3：[サブ見出し]

H2②：[見出しタイトル（キーワード含む）]
　執筆方針：
　H3：（必要な場合のみ）
（必要な数だけ展開）

## 結論
- 線引き（絞り込み）：
- 1つのアクション（CTA）：
- あえての隙・問いかけ：

## 情報量（s4lv）
- checklist 1章の3点（前提・驚く発見・情報量）を書く。比べる相手は3つまで、数字は約30個まで
```

**Step 3完了後チェックリスト（ユーザーに提示する前に必ず確認）**

「（キーワード：〜）」のような注記を付けただけでは満たしたことにならない。**見出しの文字列そのもの**を1つずつ目視で照合する。

- [ ] 各H2の見出し文に、Step 2.5で確認した検索キーワードが実際の文字列として含まれているか
- [ ] H3を使った場合、可能な範囲でキーワード（またはその自然な言い換え）が見出し文に含まれているか
- [ ] 含められなかったH2/H3があれば、その理由を1行添える（無理に詰め込んで不自然にしない）

**ユーザー承認ポイント③**
「この構成で進めますか？」と確認する。

---

## Step 4：記事本文生成

承認された構成に従い、本文を生成する。

**s4lv**：`note_article_checklist.md` 2〜6章に従う（導入は1文ごとに改行・直球のベネフィット文は使わない・改行は1〜2文ごと・読点は減らす・使わない言葉・太字は核心だけ・開示・数字の書き方）。次の「導入部は記事の命」は、s4lvでは checklist 2章が優先する（ベネフィットの言い切りは求めない）。

**導入部は記事の命（無料記事でも例外にしない）**：痛み・ベネフィット・フックを、本文のどの部分よりも時間をかけて磨く。s4lvは `note_article_checklist.md` 2章、mbticodeは専用ファイル「導入部は記事の命」に従う。

**適用するルール**
- `writing_core.md` のPASONA・5大ルール・親近感手法を適用する
- `writing_tone.md` の共通核と、該当アカウントの上書きを適用する（s4lvの改行・導入は checklist が優先）
- `CLAUDE.md` の絶対遵守ルール（Note規約・捏造禁止）を守る
- mbticodeは `mbticode_tone.md` の全ルールと、専用ファイルの品質基準・視覚フォーマットを適用する

---

## Step 4.5：審査（必須ゲート）

本文を `drafts/`（mbticodeは `articles/drafts/`）へ保存した上で、次の順で**1回ずつ**行う。

1. **機械QA**：`qa_article.py` を実行する。ERROR 0件が必須。警告は、直すか、理由をつけて許容する。s4lvでは、オーナーの意図（使わない言葉・直球のベネフィット・開示・数字の多さ・太字の記法）を機械が拾う
2. **自分の目で先回りチェック（1回）**：審査員が指摘しそうな点を潰す。段落末の同一語尾3連続／1文の読点3個／直近の記事との導入・締めの型かぶり／記事内での単語・書き出しの使い回し。s4lvは `note_article_checklist.md` 2章「使わない言葉」・4章・太字の位置。mbticodeは専用ファイルの追加項目
3. **審査を並行で起動する（初稿のみ・同じメッセージで）**
   - `note-ai-reviewer`：AIっぽさ・論理・事実（全アカウント）
   - `note-beginner-reader`：初心者になりきった読者役（**s4lvは必須**。ほかは任意）
   - 委譲文は「対象パス／種別（無料・有料）／アカウント／巡数＝1巡目」の4点だけ
4. **修正する**：BLOCK・FIX、初心者役の指摘（迷いの大きい順）。**初心者役が3点以下で、原因が「情報量」なら、書き足す直しをしない**。情報量を減らす案（比べる相手・数字・用語）をオーナーに提示して判断を仰ぐ
5. **再確認は、範囲を絞って1回**：SendMessageで、1巡目のエージェントを継続する（新規起動しない。参照ファイルの再読み込みが不要になる）。依頼文は「FIX #Nの解消確認と、新規BLOCK/FIXの有無のみ」
6. **合計3巡で必ず打ち切る**（初回＋再確認2回）。打ち切り時に残るFIXが軽微（語尾・句読点の機械的な言い換え）なら、司令塔が直接直してよい。BLOCKが残る場合、直し方に判断が要る場合は、現状・試したこと・残る理由を添えてオーナー判断に回す
7. **再審査に出さない変更**：誤字・一語の言い換え・語尾・句読点・改行の微調整・オーナー自身の手直しだけの変更は、機械QA（ERROR 0）で確定してよい。フル審査は「初稿」と「セクションの追加・削除／新しい主張／構成の変更」のときだけ
8. **`## 審査結果: PASS` が出るまで、本文をチャットに出力しない**。審査結果の表は、本文提示時に添える（残るNOTEも見せる）

---

## Step 5：ドラフト保存（必須・本文出力と同時に実行）

チェックリスト全項目通過後、ファイルを保存する。「後で保存する」は禁止。本文をユーザーに出力するのと同じターンで保存する。

- **s4lv**：`brands/s4lv/drafts/note_free_YYYYMMDD_◯◯.md`（有料は `note_paid_...`）。先頭の管理情報は、直近の下書き（`note_free_20260921_impression_pv_gap.md`）と同じ形（作成日／公開／種別／有料誘導先／Noteタグ）
- **mbticode**：専用ファイルの「Step 5」に従う

---

## Step 6：公開後の処理（ユーザーから「公開した／公開済み」の報告を受けたら必ず実行）

「削除でOK」等の指示があっても、**削除の前に必ずこのStepを先に実行する**。draftsのファイルはGit管理外（未追跡）の場合が多く、移設せず削除すると本文が完全に失われる（2026-07-29に実例あり）。

- **s4lv**：`note_article_checklist.md` 8章（URL・タグの確認→下書きの同期→index登録→意図の書き足し→公開4週後の見直し→コミットしてmainへ反映）。`published/` は作らない（indexが `drafts/` を直接参照）
- **mbticode**：専用ファイルの「Step 6」に従う

---

## 全体の流れ

```
[s4lv：資料をもらったら] checklist 0章の整合チェック（1回で質問をまとめる）
[テーマ未指定の場合] テーマ3案提案 → ✅選択
Step 1：ペルソナ設計 → ✅承認
Step 2：タイトル生成（3案）＋ Step 2.5：SEOキーワード確認（WebSearch）→ ✅タイトル承認
Step 3：見出し構成設計（前提1行・H2・H3・キーワード配置・情報量）→ ✅承認
Step 4：記事本文生成 → 保存
Step 4.5：機械QA → 自分の目で通読 → 審査を並行（note-ai-reviewer＋s4lvは note-beginner-reader）→ 修正 → 範囲を絞って再確認（合計3巡まで）
Step 5：本文提示（審査表を添える）→ 完成
[公開報告を受けたら] Step 6：公開後の処理（s4lv＝checklist 8章／mbticode＝専用ファイル）
[任意] 資産化チェック → docs/reference/note_asset_check_prompt.md
[任意] 公開前品質チェック → /notekaigi を呼び出す
```

---

## 注意事項

- 各ステップで確定済みの原則は再議論しない
- 戦略的判断が必要な場面（新アカウント設定・方針転換・想定外のテーマ）は `/notekaigi` を別途呼び出す
- アカウント情報がない場合はStep 1の前にユーザーへ確認する
- オーナーの直しの意図は、s4lvなら `note_article_checklist.md` へ、mbticodeなら専用ファイルへ、日付つきで1〜2行だけ書く（台帳・スキル本体には重ねて書かない）
