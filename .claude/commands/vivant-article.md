# vivant 記事生成システム

`/vivant-theme` の引き継ぎ情報を受けて、構成設計・本文生成・品質チェック・保存まで行うシステム。
引き継ぎ情報がない場合は「テーマ・ペルソナ・タイトル・種別を教えてください」と確認してから開始する。

junk_juiceの `/junk-article` を土台にしているが、vivantは実体験ベースではなく情報ベースで記事を作る（`vivant/rules/project_vivant_content_policy.md` 準拠）。

## 進行フロー（2026-08-01改訂）

`/vivant-theme` でタイトルが確定したら、**Step 1の構成提案を出すまでは質問で立ち止まらず一気に進める**（キャスト鮮度チェック・reference参照・構成の組み立てを含む）。判断に迷う点は自分で決めてよい。構成提案（「この構成で進めますか？」）が確認ポイントの1つ目。

**構成提案がOKになったら、Step 2（本文生成）→Step 3（品質チェック・`qa_article.py`実行含む）→Step 4（drafts保存）までを、確認を挟まず一括で実行する。** ERRORが出た場合はユーザーに提示せず自分で修正し、ERROR 0件になるまで繰り返す。

**チャットでの報告は本文全文を貼り付けず、以下のみに絞る**（2026-08-01確定）：
- 保存先パス（マークダウンリンク）
- QA結果（ERROR/WARN件数）
- 修正した点の要約（あれば）

作業工程（Step 1〜5）自体は変更しない。ユーザーが確認するのは構成提案（Step 1）のみで、それ以降はStep 4（保存）まで自動で進む。Step 5（公開後処理）はNote URLの確認が必要なため従来通り。

## アカウント概要

- **保存先**：`vivant/articles/drafts/`
- **文体・ジャンル**：`vivant/profile.md`・`vivant/examples_essay.md`（蓄積次第）を参照
- **一次情報の参照（必須）**：本文生成時は `vivant/reference/` フォルダ（放送内容・視聴率・SNS反応・SEOキーワード・登場人物等の事実情報）を必ず参照する。そこにない断定的な数字・エピソードを作らない
- **キャスト情報鮮度チェック**：`vivant/reference/vivant_characters.md` 冒頭の「最終鮮度チェック日」が7日以内、または同一セッションで直前に `/vivant-theme` を実行済みならスキップ。それ以外はWebSearchで「VIVANT 新キャスト 発表」等を簡易検索し、新キャスト・役名判明があれば追記の上、チェック日を更新する

## Step 1：構成設計

### 共通ライティングルール（参照）

- `brands/writing/writing_core.md` — PASONA・5大ルール・親近感手法
- `brands/writing/writing_headlines.md` — ケープルズ5基本ルール
- `brands/writing/writing_note_structure.md` — 3視点構造・H2設計・導入3要素
- `brands/writing/writing_expressions.md` — 表現パターン辞典

### H2設計ルール

- 各H2に「何を・どこまで具体的に書くか」の執筆方針を付ける
- H2は3〜6本に絞る（一律固定しない）
- **H2見出しの言語設計**：全H2のうち最低1本に、引き継ぎ情報の「H2組み込み候補ワード」を含める。純粋な感情語のみの見出し（何の話かわからないもの）は禁止
- ニッチ義務化：検索結果の要約記事禁止（vivantならではの整理・切り口を必ず入れる）

### H3の使用判断

H2の内容が複数の独立したサブトピック・段階・パターンに分かれる場合のみ使う（1H2につき2〜3本が上限）。

### 出力フォーマット

```
## 導入部
- ペルソナの共感ポイント（最初の3行で刺さる内容）：
- フック（続きを読ませる仕掛け）：ペルソナが実際に置かれている場面を直接描写する（「〜という声も見かけます」のような伝聞・第三者視点に逃げない）
- ベネフィット（この記事を読む理由）：「読むと読者がどう変化するか」を明示する一文を必ず入れる（「整理していきます」のような執筆側の作業宣言だけで終わらせない）
- 導入部の分量目安：3〜4段落・250〜400字程度（ペルソナの情景が伝わる最低限の厚みを確保する。ただし2026-08-01追記のAIっぽい定型描写NG例には注意）

## 本論
H2①：[見出しタイトル（キーワード含む）]
　執筆方針：
　H3：（必要な場合のみ）

H2②：[見出しタイトル]
　執筆方針：
（必要な数だけ展開）

## 結論
- 振り返り（事実と考察を軽く整理する1〜2文。「まとめると」は使わない）：
- 誠実な留保（次回で必ず解決するとは断定しない）：
```

**2026-08-01廃止**：結論末尾の放送スケジュールCTA（「第◯話は◯月◯日◯時、TBS系日曜劇場で放送されます。」等）は不要（ユーザー判断・新庄考察記事で削除・恒久適用）。結論は「振り返り→誠実な留保」で終え、その後に関連記事リンク（末尾リンクのルール参照）を置く。

「この構成で進めますか？」と確認する。

※この結論の型は2026-07-31、1本目の記事制作で確定したもの。junk_juice由来の「N（絞り込み）＋コメント誘導」の型は使わない（`vivant/examples_essay.md`の「構成の型」参照）。

## Step 2：本文生成

### 適用するルール

- `brands/writing/writing_core.md` のPASONA・5大ルール・親近感手法を適用する
- `brands/writing/writing_expressions.md` から状況に応じたパターンを選択する
- ルート `CLAUDE.md` の絶対遵守ルール（Note規約：性的描写・断定的統計・特定個人を傷つける表現の禁止）を守る
- `vivant/rules/project_vivant_content_policy.md` を守る（出典不明の数字の捏造禁止・実体験と誤認させる一人称語りの禁止）
- `vivant/examples_essay.md` のトーン・語尾ルール・構成の型に合わせる。**ただし例文として載っている具体的な文言はそのまま流用しない**。テーマが変わっても言い回しは毎回ゼロから作り、既視感（前の記事と似た表現だと感じる状態）を避ける
- **「数字＋説」という表現を使わない**（2026-08-01追加。「95%説」等は違和感があるとユーザー指摘。数値そのものではなく、それが指す論点を名付けた表現（例：「内通疑惑」）を使う）
- **語尾を終始「〜です」「〜ます」の言い切りだけにしない**（2026-08-01追加）。「〜ですよね」「〜気もします」「〜かもしれません」のような柔らかい語尾も要所で混ぜ、プロのライターとしての情報の質は保ったまま、読み手がフランクに読める温度感を作る（1文書き終えるごとに機械的に混ぜるのではなく、自然な流れの中で3〜5箇所を目安に）

### フォーマット・記号ルール

| 要素 | 使う場面 | 禁止 |
|---|---|---|
| `>` blockquote | ペルソナが持ち帰るべき事実・要点（単なる感傷的な相槌・雰囲気の締めは不可。2026-08-01改訂・`examples_essay.md`参照） | 通常の説明文・事実の羅列 |
| ` ``` ` コードブロック | 読者へのCTA・テンプレート例文 | 地の文・説明文 |
| `**` 太字 | 核心の一言・事実と考察の境目・重要な見立て（目安は`vivant/examples_essay.md`参照。太字マーカーを鉤括弧・丸括弧等の閉じ括弧、および「%」に直接隣接させない（2026-08-01改訂：`）」』】%`等も対象。`**95%**`は不可、`**95**%`のように%を外に出す）） | 説明文全般 |
| `---` | 大きな転換点のセクション区切り | 多用しない |

**X投稿の扱い**：直接URLリンクの引用は可。スクリーンショット画像の転載は不可。該当のX投稿に画像が含まれる場合、URLを単独行で本文中（言及箇所の直後）に貼ることでNote側がリンクカード化し、画像付きで表示される（2026-08-01確認）。末尾の関連記事リンクだけでなく、根拠を示したい本文中の箇所でもこの手法を使ってよい。

### CTAのルール（2026-08-01改訂：放送スケジュールCTAは廃止）

- 結論に放送スケジュール等のCTAコードブロックは入れない（ユーザー判断で恒久廃止。結論は「振り返り→誠実な留保」で終える）
- コメントを促す一文は入れない（2026-07-31確定。理由は`vivant/examples_essay.md`「構成の型」参照）
- 「答え合わせは次回に」のような、次話で必ず解決するという確約は避ける（2026-07-31、1本目記事で確約表現がNGと判明。この方針自体は継続）

### 関連記事リンクのルール（2026-07-31確定）

- **末尾（結論CTAの直後・記事の最後）**：関連する自分の既存記事があれば、テキストリンクを**必ず1本**入れる（`articles/published/`・`article_index.md`から選ぶ）。**有料記事が存在する場合は有料記事を優先**する。存在しなければ関連度の高い無料記事から選ぶ。関連する既存記事がまだない場合は省略してよい
- **本文中と末尾で同じ記事へのリンクを重複させない**（2026-08-01追加）。公開済み記事が複数あり、本文中に自然に組み込める関連記事リンクをすでに入れている場合、末尾はそれとは別の記事を選ぶ（無理に別記事へ差し替える必要はなく、自然に選べる範囲で分散させる）
- **本文中**：話の流れに自然に組み込める関連記事があれば、該当セクション内にも追加でテキストリンクを入れてよい（必須ではない・無理に入れない）。**人物名・固有名詞そのものをリンク化しない**（2026-08-01改訂：「本当の上司は[長野専務](URL)なのではないか」のような形だと関連記事への誘導だと気づきにくいとユーザー指摘）。「〜はこちらで整理しています」「詳しくは〜の記事へ」のように、リンクだと分かる文言を添えて貼る
- リンク形式：`[記事タイトル](Note URL)`。Note編集画面では手動でテキストにリンクを設定する必要がある旨をユーザーに伝える（Markdownのままでは自動リンク化されない）
- **末尾のリンクはカード化を基本とする（2026-07-31確定）**：末尾は`[記事タイトル](URL)`ではなく裸URL単独行で記載する。Noteはリンクカード化を「URL単体をその場でペーストした瞬間」にのみ発動するため、記事全体をまとめて貼り付けただけではカード化されない。ユーザーには「記事全体を貼り付けた後、末尾URL行だけ一度削除してURLだけを単体で貼り直すとカード化される」と案内する

### タイトルの扱い（2026-07-31確定）

本文内にH1見出し（`# タイトル`）としてタイトルを重複表記しない。確定タイトルは管理情報ヘッダー（Step 4）にのみ記載し、本文は冒頭の注意書きから直接始める（Note側のタイトル欄と重複するため）。

### 冒頭の注意書き（必須・2026-07-31改訂）

本文冒頭（導入部の前）に、`>` blockquoteで以下を含む注記を置く。**長くなりすぎないよう、情報の時点とネタバレ警告は1文にまとめる**（「〜第◯話までの内容をもとに」ではなく「〜第◯話までのネタバレを含みます」とすることで、時点情報と警告を同時に伝える）：
- 情報の時点＋ネタバレを含む旨（1文にまとめる。例：「本記事は『VIVANT』第◯話（放送日）までのネタバレを含みます。」）
- 考察部分は個人の見解であり公式見解ではない旨（`rules/project_vivant_copyright_and_monetization.md`準拠）
- 今後の展開で内容が変わる可能性がある旨

不要な重複表現（「事実と考察は分けて書いていますが」等の前置き、時点情報の二重表記）は削り、3要素を3文程度に収める。

**表記ルール（2026-07-31確定）**：「日曜劇場」という表記は注意書きでは使わない（`『VIVANT』第◯話`のように作品名のみで表記する）。

**例文（2026-07-31確定）**：
```
※本記事は『VIVANT』第2シーズン第11話（2026年7月26日放送）までのネタバレを含みます。考察部分は個人の見解であり、公式見解ではありません。今後の展開で内容が変わる可能性があります。
```

### 記事末尾のフッター（2026-07-31廃止）

「VIVANTの伏線・考察メモ／Note：https://note.com/s4lv24」という定型フッターは**不要**。Note側でアカウントプロフィールカードが自動表示されるため、本文側に重ねて書かない。

### 文字数目安（2026-08-01改訂・notekaigi確定）

**無料記事は上限を設けない**。下限のみ2,500字とし、実際の文字数は「そのテーマで出すべき情報を出し切ったか」で判断する（文字数を埋めるための水増し・冗長な言い換えは禁止）。有料記事は従来通り価格帯別の目安・下限を維持する。

| 記事の型 | 目安 | 下限 |
|---|---|---|
| 通常無料記事 | 下限のみ（上限なし） | 2,500字 |
| 有料記事（200円） | 4,500〜5,500字 | 4,500字 |
| 有料記事（300円） | 6,000〜7,000字 | 5,500字 |
| 有料記事（500円〜） | 8,000字以上 | 7,000字 |

**有料記事の無料：有料比率（価格共通）**：無料3：有料7

**改訂の背景**：従来の「2,500〜3,500字」はjunk_juiceの`/junk-article`テンプレートを流用した基準で、vivant固有の読者層・記事の型に基づく根拠がなかった。vivantにはまだ読了率・離脱率の実測データもないため、notekaigiにて「上限は撤廃し、情報を出し切ることを優先する」方針に転換した（下限は「情報が薄いと感じさせないための最低ライン」としてユーザー判断により2,500字を維持）。詳細は`vivant/rules/project_vivant_free_article_length_0801.md`参照。

**文字数のカウント範囲（2026-08-01確認）**：文字数は管理情報ヘッダー（作成日〜Noteタグの行）を含めず、`---`区切り線より後の本文（冒頭の注意書き〜末尾の関連記事リンクまで）のみを対象とする。

## 有料記事モード（種別に「有料記事」が指定された場合のみ適用）

**現在未使用**：2026-07-31時点、vivantは無料記事のみを運用中（`vivant/rules/project_vivant_copyright_and_monetization.md`参照）。有料記事の着手が決まるまで、以下は読み飛ばしてよい。

### 全体構造

有料記事は「無料パート」→「誘導文」→「ペイウォール」→「有料パート」の4層で構成する。

```
[無料パート] 読者を「欲しい」状態まで持ち込む
     ↓
[誘導文] 2〜3行・煽らない・何があるかを一言で告知
     ↓
[--- ※ここから有料パートです（Noteで公開時に有料ラインを設定する）]
     ↓
[有料パート] 情報 × 具体的手順 × チェックリスト
```

### 無料パートの設計（Step 2で適用）

1. 読者への問いかけ：ペルソナの悩み・疑問を代弁する（3〜5行）
2. 共感のブリッジ
3. 課題・疑問の具体的な情景描写（200〜250字）
4. 「でも解決できる」との対比提示（150字）
5. この記事で何が解決するかの具体告知（150字）
6. N（絞り込み）
7. 誘導文：「[テーマ概要]、全部これから話す。[付加価値の一言]。続きをどうぞ。」

### 有料パートの設計（Step 1構成設計＋Step 2本文生成で適用）

**独自情報基準**：「ちょっと調べれば出てくる一般論」はNG。出典を示せる具体的な情報・整理された手順・チェックリストなど「読者がここでしか得られない」と感じる情報密度が必要（`vivant/rules/project_vivant_content_policy.md` の情報正確性ルールに従う）。

**チェックリストの品質基準**：
- 「あ、これ考えてなかった」と読者が思う項目のみ追加する
- 目安：15〜20項目（価格が上がるほど増やす）

**--- の使用ルール（有料記事）**：エピソード・セクション切り替えのシグナルとして使う（合計3〜4か所、フッター前の`---`含む）。

## Step 3：品質チェック

本文生成後にチェック。問題があれば修正してから保存する。

**【資産性】**
- [ ] 読後にコメント・フォロー・シェアしたくなる余白があるか
- [ ] 「vivantならでは」の整理・切り口が入っているか
- [ ] 将来の有料記事への導線になっているか

**【読みやすさ・拡散】**（2026-08-01強化：3本目記事で以下が未検出のまま提示し、ユーザー指摘で3往復の手戻りが発生したため明文化）
- [ ] 最初の3行以内に共感フックがあるか
- [ ] ありきたりな一般論の要約で終わっていないか
- [ ] 導入部のフックが「ペルソナ自身の場面」として直接描写されているか（伝聞形「〜という声も見かけます」だけで済ませていないか）
- [ ] ベネフィットが「読後にどう変化するか」という形で明示されているか（「整理していきます」等の作業宣言だけで終わっていないか）
- [ ] 導入部の分量が薄すぎないか（目安250〜400字。結論の説明にすぐ入っていないか）
- [ ] AIっぽい定型描写になっていないか（時間経過を律儀に演出する情景描写・取ってつけた接続語・自問自答の締めパターンの多用。`examples_essay.md`のNG例参照）
- [ ] テーマの深刻度と感情表現の強さが釣り合っているか（ドラマ考察のような軽いテーマを、生活に支障が出るような深刻な悩みとして誇張していないか）
- [ ] 予告・映像描写について「実際に映っているもの」と「ナレーション・テロップ等で伝えられているだけの情報」を混同していないか（`rules/project_vivant_content_policy.md`の事実描写の精度ルール準拠）

**【フォーマット・スマホ縦読み】**
- [ ] 文字数を理由に情報を削っていないか（無料記事は下限2,500字未満の場合、情報が薄い可能性を疑う）
- [ ] 文字数を埋めるための冗長な言い換え・重複説明が入っていないか（無料記事は上限なしだが、水増しは禁止）
- [ ] `>` blockquoteが「ペルソナが持ち帰るべき事実・要点」に使われているか（2026-08-01改訂：単なる感傷的な相槌・雰囲気の締めは不可）
- [ ] blockquoteが全H2に最低1箇所ずつ入っているか、特定セクションに偏っていないか（2026-08-01追加：過去記事は3〜15箇所の実績があり、2箇所以下は手薄と疑う）
- [ ] 複数の根拠・視点を列挙する箇所は、`>` blockquoteで囲んで引用ブロック化する余地がないか検討したか（自然な場合のみ・無理に囲まない）
- [ ] 項目数が明確に数えられるリストは「・」だけでなく「①②③④」も検討したか
- [ ] 太字マーカーが鉤括弧・丸括弧・「%」に直接隣接していないか（`**「text」**`・`**95%**`になっていないか）
- [ ] 太字とblockquoteの数のバランスが取れているか（太字7〜9箇所・blockquoteは全H2に分散、`vivant/examples_essay.md`参照）

## Step 5：公開後の処理（ユーザーから「公開した／公開済み」の報告を受けたら必ず実行）

**2026-08-01確定**：ユーザーから「公開しました」の一言を受けたら、以下の手順1〜6を確認を挟まず自動で一括実行する（削除の是非を都度確認しない）。Note URLがまだ分かっていない場合のみ、手順1でURLを聞く（・有料記事なら価格も）。

「削除でOK」等の指示があっても、**削除の前に必ずこのStepを先に実行する**。draftsのファイルはGit管理外（未追跡）の場合が多く、published/へ移設せず削除すると本文が完全に失われる。

**手順**
1. ユーザーから Note URL（・有料記事なら価格）を確認する（未確認の場合のみ聞く）
2. **公開後の差分照合（2026-07-31確定）**：ブラウザでNote URLを開き、DOM（`strong`/`b`・`a`・タグ一覧）を確認し、ドラフトと比較する。太字・リンク・Noteタグ等でユーザーが公開時に手動調整した箇所があれば、指摘を待たずドラフト側に反映する（qa_article.pyでは検知できない項目のため）。get_page_text等の要約系ツールはblockquoteを太字と誤認することがあるため、実際の判定はDOM（`querySelectorAll('strong,b')`等）で行う
3. `vivant/articles/published/` に `NN_【無料/有料】タイトル.md` の形式でファイルを作成する（NNは`article_index.md`の次の管理No）
4. ヘッダーに管理No・価格・ステータス（公開済み＋日付）・URLを記載する
5. `vivant/articles/article_index.md` に1行追加する（管理No／タイトル略称／URL／価格／公開日）
6. **上記1〜5が完了して初めて** `articles/drafts/` の元ファイルを削除する（2026-08-01確定：確認を挟まず自動で削除する）
