# /journal — 音声ジャーナル資産化パイプライン

ユーザーが貼り付けた音声ジャーナル（思考ログの文字起こし）を、①クレンジング＆整形 → ②構造化・分類 → ③分析・Next Action提案 の3ステップで自動処理し、`journals/` へ資産として蓄積する。

> 全体設計・ディレクトリ構成は `journals/CLAUDE.md` を参照。処理対象はユーザー自身の思考であり、基本的に全面受容する（`docs/business_inventory.md`等の既存業務のような承認フローは挟まない）。ただし方針バッティング検知（Step 4）だけは必ず行う。

テキストが貼られていない場合は「文字起こしテキストを貼り付けてください」と一言だけ伝えて待つ。
指示なしで長い未整形テキストが貼られた場合は、`/journal`として処理してよいか一言確認してから進める（黙って推測しない）。

## 入力

1. 文字起こしテキスト（必須）
2. 対象日付（省略可・省略時は当日 = システムの`currentDate`）
3. 録音時刻（省略可・分かれば見出しに使う。不明なら処理時刻を使う）

同じ日付に対して2回目以降の`/journal`が来た場合は「追記」として扱う（上書きしない）。

---

## Step 1: クレンジング＆整形

- フィラー（えーと・あの・まあ・うーん等）・言い淀み・重複を除去し、誤字脱字を修正する
- **やらないこと**：意見の言い換え・結論の補強・主張の追加。捏造禁止の精神をそのまま適用し、発言していないことを足さない。話の順序も、意味が変わらない範囲を超えて再構成しない
- 保存：
  - 生データ → `journals/daily/raw/YYYY-MM-DD.txt`（新規なら作成、同日追記なら`----- HH:MM -----`区切りで追記）
  - クレンジング済み → `journals/daily/YYYY-MM-DD.md`（新規なら見出し付きで作成、同日追記なら`## HH:MM`見出しで追記）

## Step 2: 構造化・分類

クレンジング済みテキストを読み、以下5分類に該当する内容を抽出する（該当なしの分類があってよい。無理に埋めない）。

| 分類 | 内容 | 保存先インデックス |
|---|---|---|
| アイデア | まだタスク化されていない着想・思いつき | `journals/ideas.md` |
| タスク | 具体的な行動として切り出せるもの | `journals/tasks.md`（チェックボックス形式） |
| 気付き | 自分の傾向・パターンについてのメタ認知的な発見 | `journals/insights.md` |
| ブログ/SNSネタ | コンテンツの具体的な切り口。分かれば候補先アカウント（shira_note/cf_room/vtuber_log/vivant/s4lv/mbticode/junk_juice/未定）をタグ付け | `journals/content_seeds.md` |
| 長期テーマ | 繰り返し出てくる大きなテーマ | `journals/themes.md`（新規テーマのみ見出し新設。既存テーマは追記） |

各抽出項目は「内容 — 由来: journals/daily/YYYY-MM-DD.md」の形で該当インデックスに追記する。
併せて `journals/daily/YYYY-MM-DD.md` 側にも `## 抽出結果` セクションを作り、その日/その回に何をどこへ振り分けたかを埋め込む（インデックス側の更新が将来漏れてもdaily単体で追跡できるようにする）。

## Step 3: 分析・Next Action提案

`journals/daily/YYYY-MM-DD.md` に `## 分析` セクションを追加し、以下を書く。

- **メタ認知**：今回の話し方・迷い方・繰り返し出てきた視点など、内容そのものより一段上の観察（1〜3点）
- **Next Action**：最小労力で着手できる次の一歩を1〜3個。対応するタスク/アイデアへの参照をつける

この`## 分析`セクションは保存するだけでなく、チャット上の報告にもそのまま出す。

## Step 4: 方針バッティング検証（省略不可）

Step 2〜3で抽出した内容について、話題に関連しそうな既存の基盤ファイルとの矛盾がないか確認する。全ファイルを毎回総当りする必要はなく、話題から推測できる範囲でよい（例：SNS運用の話が出たら該当ブランドの`rules/`、記事の方針転換の話が出たら`rewrite_common_rules.md`や`docs/systems/`）。

- 主な確認候補：ルート`CLAUDE.md`の行動規範、`brands/writing/writing_core.md`、各アカウントの`rules/`・`profile.md`、`blogs/*/rewrite_common_rules.md`、`docs/systems/`の会議システム定義
- **矛盾を見つけても、対象ファイルを勝手に書き換えない。** 該当アイデア/タスク自体は通常どおりStep 2のインデックスに記録した上で、以下を行う：
  1. チャット上で「この思考は現在の基盤（〇〇）と衝突する可能性がありますが、方針をアップデートしますか？」と具体的に確認する（該当ファイル名・矛盾点を明示）
  2. `journals/collision_log.md` に検知内容を1行追記する（ユーザーの判断欄は回答後に埋める）
- 矛盾がなければ「バッティング検知：なし」とだけ報告する（無理に絞り出さない）

---

## 出力フォーマット（チャット報告・毎回この順）

```
## 保存
- 生データ: journals/daily/raw/YYYY-MM-DD.txt
- 整形済み: journals/daily/YYYY-MM-DD.md

## 抽出件数
アイデア n件 / タスク n件 / 気付き n件 / ネタ n件 / 長期テーマ n件（新規n・既存継続n）

## 方針バッティング検知
なし／または具体的な確認事項

## 分析・Next Action
（Step 3の内容をそのまま）
```

## 完了条件

- `journals/daily/raw/YYYY-MM-DD.txt` と `journals/daily/YYYY-MM-DD.md` が保存済み
- 該当する横断インデックス（該当分類のみでよい）に反映済み
- バッティングを検知した場合はユーザーへ確認済み（`collision_log.md`記録は確認と同時に行う。回答待ちのまま完了報告しない）
